# Phase 15.2: Code Review Report

**Reviewed:** 2026-06-05
**Depth:** standard
**Files Reviewed:** 14 (focused on the highest-risk theming-engine + IA-state files; the long-tail conformance screen edits are font-size/back-intent token swaps that scanned clean)
**Status:** issues_found

## Summary

The theming engine and IA-state changes for this phase are, frankly, well-built. The two
recurring project traps were the explicit risk going in — Compose write-scope cancellation and
read-then-write lost updates — and both are handled correctly and consistently across every new
persistence path:

- Every durable theme/profile write routes through the process-lifetime `AppContainer.writeScope` +
  an atomic single-`edit` read-modify-write (`mutateActiveProfile` / `ThemePrefs.mutateOverrides`).
  No new persistence write lands on a composition `rememberCoroutineScope()`; the only
  `rememberCoroutineScope()` survivors (FilesScreen, PrintersScreen mDNS scan, AppShell, SpoolScreen)
  are non-durable/transient by design.
- `effectiveTokens` is a **pure** bake of the canonical `activeThemeTuple` in BOTH branches via
  `ThemeResolver.bake` — it never reads the async-lagged `resolver.tokens`, exactly as the HIGH-1/2
  contract requires. The override merge uses `base.copy(...)` so no axis can be silently dropped.
- The override-step intents (`updateThemeOverride`) use `MutableStateFlow.update`, so rapid taps
  read the live value and can't drop an axis.
- Token purity holds: `OutlinedControl` and the reviewed control screens route all color through
  `LocalTokens`; the only raw-`Color(0x..)` hits are sanctioned data carve-outs (the spool palette
  grid, the prompt `<color:>` author hex, and a contrast-ink pick against an arbitrary data-swatch
  fill in `ThemeEditorScreen`).
- `BedMeshHeatmapView.onDraw` is allocation-free; the 32 OKLCH conversions are baked once in
  `applyTokens`, and `OklchRamp.themedRampStops` returns an `IntArray` (no per-cell Color alloc).
- All `String.format`/`%06X` uses pass `Locale.US`. No empty catches, no hardcoded secrets; apiKey
  is redacted in both `Profile.toString` and `PersistedProfile.toString`.

The findings below are a genuine drag bug in the dev overlay, a latent stale-config feeding the
webcam URL resolver, the owner-deferred (undiagnosed) webcam crash, and minor doc/nit items.

## Warnings

### WR-01: Dev overlay panel-drag does not accumulate — chip snaps back to start of gesture

**File:** `app/src/main/java/works/mees/dinghy/ui/shell/DevThemeCyclerOverlay.kt:178-208`
**Issue:** The draggable position uses `var offset by remember { mutableStateOf<Offset?>(null) }`
and computes `val pos = offset ?: Offset(start, start)` per recomposition. Inside
`pointerInput(boxSize) { awaitEachGesture { drag(down.id) { change -> offset = Offset(pos.x + delta.x, pos.y + delta.y) } } }`, the captured `pos` is fixed for the lifetime of the running gesture
coroutine (it only re-reads when `pointerInput` restarts, keyed on `boxSize` — which doesn't change
during a drag). `change.positionChange()` returns the **incremental** delta since the previous
pointer event, so `offset = pos + delta` repeatedly sets the position to *gesture-start + last
single-event delta*, not *start + cumulative delta*. The panel lags/snaps toward the start of the
gesture instead of tracking the finger. This is dev-only chrome (gated behind the dev-enable
toggle), so it does not affect shipped users — but it's a real motion bug in a tool meant for the
cross-printer conformance walk. (A 15.2-04 commit already disabled chip-tap bleed into this drag;
the drag itself remains broken.)
**Fix:** Accumulate into the live state rather than the captured snapshot:
```kotlin
drag(down.id) { change ->
    val delta = change.positionChange()
    offset = Offset(
        ((offset ?: Offset(startInsetPx, startInsetPx)).x + delta.x).coerceIn(0f, maxX),
        ((offset ?: Offset(startInsetPx, startInsetPx)).y + delta.y).coerceIn(0f, maxY),
    )
    change.consume()
}
```
Reading `offset` (the state) inside the lambda each event makes the deltas accumulate correctly.

### WR-02: Webcam URL resolution reads the write-dead legacy `connectionStore`, not the active profile

**File:** `app/src/main/java/works/mees/dinghy/ui/shell/AppShell.kt:194-226`
**Issue:** The webcam holder still resolves feed URLs from
`container.connectionStore.config` (`val cfg by ...; val activeCfg = cfg ?: ConnectionConfig(host = "")`),
and keys the holder on `activeCfg.host`. But `connectionStore` is never written anywhere in the
codebase any more — a repo-wide grep finds exactly one consumer (this line) and zero setters; all
connection persistence migrated to `profileStore` in Phase 14 (and `connectionStore` is explicitly
marked "dead but retained until the phase is verified", AppContainer.kt:95). With nothing writing
it, `cfg` resolves to `null` and `activeCfg.host` is `""`, so the holder is built against an empty
host. Note this is a **pre-existing Phase-14 migration gap** (the `cfg`/`activeCfg` region was not
touched in 15.2 — `git diff d216100..HEAD` shows no change there), but 15.2-03/04 actively reworked
the webcam-tile gating immediately adjacent to it (`webcamTileEnabled`, per-profile `webcamEnabled`),
and it is a live correctness defect: a per-profile webcam URL will not follow a profile switch
because the URL base comes from the wrong (empty) store. Provenance is honest here — flag it, but it
predates this phase.
**Fix:** Resolve the webcam URL base off the active profile's connection config instead of the
legacy store, e.g.:
```kotlin
val activeCfg by container.activeConfig.collectAsStateWithLifecycle(initialValue = null)
val cfgForWebcam = activeCfg ?: ConnectionConfig(host = "")
```
and re-key the holder on `cfgForWebcam.host`. Then delete the unused `connectionStore` read (and
the field, once Phase-14 verification closes per AppContainer.kt:95). Confirm against on-device
webcam UAT since the snapshot path was previously live-proven.

### WR-03: Webcam screen crashes (undiagnosed) — owner-deferred but unresolved

**File:** `app/src/main/java/works/mees/dinghy/ui/webcam/WebcamScreen.kt` (crash site not yet
isolated — likely in the holder/decode layer, not this composable)
**Issue:** The 15.2-06 on-device conformance sweep recorded a hard **crash when opening the Webcam
tile** on flox (`.planning/todos/pending/2026-06-05-webcam-screen-crash.md`), captured with no stack
trace and deferred to Phase 20 (WebRTC camera) by owner decision. `WebcamScreen.kt` itself reviews
clean — it is fully null-safe (`vm.selected?.…`, `isPortraitFeed` guards empty/garbage aspect ratios
and zero/negative dimensions, `cam.name.ifBlank`). The crash is therefore almost certainly in the
decode/poll layer (`WebcamHolder`/`WebcamView`), which is out of this phase's edited scope and
exercised on WebRTC-only printers where MJPEG can't connect. Recording it as a Warning because an
adversarial review should not let a known crash pass silently even when the owner has accepted the
defer — it is a real crash, just triaged to a later phase.
**Fix:** Capture `adb logcat` while opening the Webcam tile to get the stack trace, then guard the
decode entry point. Track via the existing Phase-20 todo; do not close 15.2 verification as "clean"
on the webcam surface.

### WR-04: `effectiveTokens` initial value is hardcoded dark — light-theme users get a startup flash

**File:** `app/src/main/java/works/mees/dinghy/theme/compose/DinghyTheme.kt:44`
**Issue:** `val tokens by tokensFlow.collectAsStateWithLifecycle(initialValue = TokensDark)`. The
first frame before the persisted tuple bakes always renders the dark token set. A user whose saved
profile is light-mode sees a brief dark flash on every cold start / process restart. Low-severity
cosmetic, but on the target appliance (always-on wall tablet) a restart flash is noticeable. The
resolver's own fail-safe already picks `TokensDark`/`TokensLight` by the `dark` flag, so the
asymmetry is only at this Compose seam.
**Fix:** This is hard to fix perfectly without a synchronous first read (DataStore is async), so it
may be acceptable. If undesired, seed the initial value from a cheap synchronous default that
matches the most-recent persisted polarity (e.g. a `SharedPreferences`-backed "last dark" hint
written alongside the DataStore tuple), or accept and document it. Flagging so the trade-off is a
decision, not an accident.

### IN-02: `connectionStore` is dead weight in `AppContainer` (and read once incorrectly)

**File:** `app/src/main/java/works/mees/dinghy/di/AppContainer.kt:88-89`
**Issue:** `connectionStore` is constructed and self-documented as "dead but retained until the phase
is verified" (line 95). Its only live reader is the buggy webcam path in WR-02. Carrying a
write-dead store that one consumer still reads is exactly how WR-02 slipped through. Not a defect on
its own, but it's a latent footgun.
**Fix:** Once Phase-14 verification closes, delete `connectionStore` (and its DataStore wiring) after
repointing the webcam reader (WR-02). Until then, leave a `@Deprecated`/grep-able marker so no new
consumer attaches to it.

### IN-03: `BedMeshHeatmapView.OPAQUE_BLACK` placeholder constant defined but only used in `lerpArgb` masking

**Issue:** `OPAQUE_BLACK` is documented as "the pre-applyTokens ramp fields" placeholder, but the
