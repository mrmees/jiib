# Phase 18.2: Code Review Report

**Reviewed:** 2026-06-07
**Depth:** standard
**Files Reviewed:** 17
**Status:** issues_found

## Summary

A clean, well-documented branding phase. The core risk areas all check out:

- **`brandTint` math is correct.** `Color.luminance()` returns linearized WCAG relative luminance in [0,1]; the `(Lmax+0.05)/(Lmin+0.05)` ratio and the `>= 3.0` floor are the right formula and the right (large-graphic, not small-text) bar. The host test suite mirrors the math independently and covers the boundary, identity, and max-contrast cases.
- **Vector drawables are sound.** pathData is valid (circles correctly converted to two-arc form), content fits each declared viewport (lockup 600×600, wordmark 433×289, foreground 108×108 safe zone), and flattening every shape to `#FFFFFFFF` is the correct enabler for `Icon(tint=…)` uniform recolor.
- **Adaptive-icon wiring is correct.** `mipmap-anydpi-v26` (adaptive) wins on API 26+, bare `mipmap-anydpi` (navy-box vector) is the API 23–25 fallback, and there are no PNG density mipmaps to shadow them. monochrome reuses the safe-zone-positioned foreground, which is correct.
- **Compose layout is not distorted.** `Icon` → `Modifier.paint(ContentScale.Fit)` derives the open (height) dimension from the fixed (width) dimension preserving aspect, so `fillMaxWidth(f) + wrapContentHeight()` renders both marks at their true aspect rather than stretching to a 600dp/289 intrinsic.
- **AAPT2 string escaping is correct.** The `about_jib_note` CDATA wrapper legitimately exempts the embedded `"` and `jib's` apostrophe; the `…` is the literal ellipsis char. Build-green confirms.

The findings below are brand-consistency leaks and minor a11y/icon-quality nits — none block the rebrand.

## Warnings

### WR-01: App still identifies to Moonraker as "Dinghy Display"

**File:** `app/src/main/java/works/mees/dinghy/net/MoonrakerSession.kt:80`
**Issue:** The phase swapped every *in-app* brand surface to "jiib" (app label, notification title, splash lockup, About wordmark, gallery header), but the `server.connection_identify` `client_name` default is still `"Dinghy Display"`. This string is sent to the printer and is rendered in Moonraker/Fluidd/Mainsail's connected-clients list — a user-visible surface. It is also baked into golden fixtures (`app/src/test/resources/golden/adversarial_auth_identify_error.json:7`, `spoolman-live-ender5-notify.json:11`). This file is outside the changed-file set, so it may be a deliberate scope decision ("repo/package stay"), but the brand now leaks inconsistently on the printer side.
**Fix:** If the rebrand is meant to cover what the *printer owner* sees, change the default to `"jiib"` and update the two golden fixtures accordingly. If intentionally retained, add a one-line note to the phase SUMMARY recording that `client_name` is deliberately left as the legacy identifier so this isn't re-flagged later.

### WR-02: Foreground brand notification still uses an unrelated Bluetooth system glyph

**File:** `app/src/main/java/works/mees/dinghy/service/MoonrakerService.kt:279`
**Issue:** The persistent FGS notification — whose title this phase just rebranded to `@string/app_name` ("jiib") — sets `setSmallIcon(android.R.drawable.stat_sys_data_bluetooth)`. A Bluetooth glyph next to the "jiib" title is brand-incoherent (the connection is a LAN websocket, not Bluetooth) and is the most persistent brand surface in the OS shell. The glyph line was not edited this phase, but it sits in the same `buildNotification` block as the title swap and undercuts the rebrand it accompanies.
**Fix:** Provide a small monochrome status icon derived from the jiib sail mark (a 24dp tintable white-on-transparent vector) and reference it, e.g. `setSmallIcon(R.drawable.ic_jiib_status)`. Status small-icons must be a single-color silhouette; the existing `ic_jiib_foreground` is sized for the 108 launcher safe zone and is not a drop-in.

### WR-03: Wordmark/lockup tint trusts that `text` clears the background, but only `accent` is contrast-checked

**File:** `app/src/main/java/works/mees/dinghy/theme/BrandTint.kt:33-40`
**Issue:** `brandTint` falls back to `text` when `accent` fails the 3:1 floor against `bg`, on the assumption that `text` is always legible on `bg`. For the built-in themes this holds, but the project explicitly supports **user-custom themes** (the entire reason this guard exists — see the KDoc's "on a user-CUSTOM theme the accent can land too close to bg"). A custom palette whose `text` is *also* low-contrast against `bg` would make the helper fall back to an equally-invisible mark. The fallback is unguarded.
**Fix:** This is a known-narrow risk (the theme system likely floors text contrast elsewhere), so a guard or an assertion is optional — but document the invariant. Either add a comment that `text`-vs-`bg` legibility is guaranteed upstream by the theme generator, or harden: `if accent passes → accent; else if text passes → text; else bg-relative black/white`. At minimum confirm the custom-theme generator enforces a text/bg contrast floor so this assumption is real.

## Info

### IN-01: Brand-mark contentDescription lacks role context

**File:** `app/src/main/res/values/strings.xml:42`
**Issue:** `cd_jiib_logo` = "jiib" is reused as the `contentDescription` for both the splash icon+wordmark **lockup** and the About **wordmark**. TalkBack will announce just "jiib" with no indication it is a logo/brand mark. For a decorative brand element this is acceptable, but "jiib logo" reads more clearly.
**Fix:** Either set the value to `"jiib logo"`, or — since both marks are decorative and the app name is conveyed elsewhere on each screen — pass `contentDescription = null` to mark them decorative and skip the announcement entirely.

### IN-02: Adaptive foreground mark nearly fills the safe-zone edge to edge

**File:** `app/src/main/res/drawable/ic_jiib_foreground.xml:8`
**Issue:** With `scale 0.16 + translate (11.0, 22.4)`, the sail mark spans roughly x:[21.6, 86.4], y:[25.6, 83.6] in the 108 canvas. The recommended adaptive-icon safe zone is the central 66dp circle; the mark's ~65dp width runs right up to the [18, 90] guaranteed-visible edges, leaving little margin before the various OEM mask shapes (circle/squircle/teardrop) start clipping corners of the outermost dots/sail tip.
**Fix:** Consider nudging the scale down (e.g. 0.15) and re-centering so the mark sits comfortably inside a 66dp safe circle. Verify on-device against a circular *and* a squircle mask before sign-off (the existing preview matrix only covers the in-app marks, not the launcher mask).

### IN-03: `wrapContentHeight()` on the splash lockup is redundant

**File:** `app/src/main/java/works/mees/dinghy/ui/screen/SplashScreen.kt:188`
**Issue:** `SplashBrandLockup` applies `.fillMaxWidth(0.6f).wrapContentHeight()`. Because `Icon` paints with `ContentScale.Fit` and derives the open dimension from the fixed width, the `wrapContentHeight()` is a no-op here (height is already content-derived). Harmless, but the KDoc's "wraps its … height so it never stretches" credits the modifier with behavior that actually comes from `paint`/`ContentScale.Fit`. The About wordmark correctly omits it.
**Fix:** Drop `.wrapContentHeight()` for consistency with `AboutWordmark`, or leave it and trim the KDoc claim.
