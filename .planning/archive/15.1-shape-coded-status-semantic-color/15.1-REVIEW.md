# Phase 15.1: Code Review Report

**Reviewed:** 2026-06-05T21:40:10Z
**Depth:** standard
**Files Reviewed:** 15
**Status:** issues_found

## Summary

Reviewed the semantic-color + shape-coded-status phase: the OKLCH bed-mesh ramp baker, the
accent-led N-series `seriesColor` helper, the status-slot override path (StatusSlot / ThemePrefs /
TokenBridge / AppContainer intents), and the shape-glyph consumers (Console, Move, PrintStatus,
ThemeEditor, Temperature).

The hot-path performance concerns called out in the brief are handled correctly:
- `BedMeshHeatmapView.onDraw` does ZERO OKLCH math per cell — the 32-stop ramp is baked once at
  construction (`OklchRamp.bedMeshRampStops()`), and `rampColor`/`lerpArgb` are pure integer ops with
  no allocation. `cellPaint`/`cellRect` are reused. Correct.
- `GraphView.onDraw` reuses pre-allocated `Path`/`Paint` per trace, rewinds rather than reallocates.
- `seriesColor` carries the empty-pool guard (falls back to accent, never `% 0`) and rejects negative
  indices via `require`.
- Every persistence write in `AppContainer` and `ThemeEditorScreen` routes through `writeScope` +
  `mutateActiveProfile`/`mutateOverrides` — NO `rememberCoroutineScope()` persistence write was found.
  The recurring write-scope-cancellation trap is correctly avoided.
- The status-override fail-safe path (`sanitizeTuple` per-entry drop, mode-gating in `TokenBridge`) is
  well-tested and sound. Status keys correctly ride the same String→Long map as pool indices without
  colliding.

No BLOCKER-tier defects. Findings are correctness edge cases, a dead/orphaned setter, and stale
documentation that misleads future maintainers. The strongest concerns are the unreachable `setMaxItems`
write surface and a `Color.hsv` value-truncation edge that can silently drop a user's picked status hue.

## Warnings

### WR-01: `maxItems` is persistable and resolvable but has no live write surface — orphaned setting

**File:** `app/src/main/java/works/mees/dinghy/theme/ThemePrefs.kt:76-78`, `app/src/main/java/works/mees/dinghy/di/AppContainer.kt` (no `setActiveMaxItems`)
**Issue:** `ThemePrefs.setMaxItems(maxItems: Int)` exists, `KEY_MAX_ITEMS` is persisted, `sanitizeTuple`
validates `maxItems` against `MAX_ITEMS_RANGE` (1..64), `ThemeResolver` threads it into
`Palette.generate`, and `Profile.maxItems` round-trips it. But there is NO `AppContainer.setActiveMaxItems`
intent and no UI control in `ThemeEditorScreen` that ever changes it — `resetActiveTheme` only ever sets
it back to `DEFAULT_MAX_ITEMS`. The entire pool-size axis is dead: a user can never change how many data
colors the pool generates. `setMaxItems` is reachable only by tests. Either the feature is incomplete
(no editor) or `setMaxItems` is dead code. The pool override grid hardcodes `t.pool.take(4)` everywhere
(ThemeEditorScreen.kt:280, 293), so even if `maxItems` were editable the editor would only ever surface 4
slots.
**Fix:** Decide intent. If pool-size is in scope, add `AppContainer.setActiveMaxItems(active, n)` +
an editor control, and make the override grid iterate `t.pool` rather than `.take(4)`. If it is out of
scope for 15.1, mark `setMaxItems` `@Deprecated`/`@VisibleForTesting` or remove it so the dead write
surface does not imply a working feature.

### WR-02: `hueToArgbLong` / `hueToHex` discard saturation/value — picked status & pool colors are always full-sat/full-bright

**File:** `app/src/main/java/works/mees/dinghy/ui/screen/ThemeEditorScreen.kt:581-592`
**Issue:** Both helpers reconstruct the color from `Color.hsv(hue, 1f, 1f)` — only the hue is captured
from the wheel; saturation and value are hardcoded to 1.0. When a slot picker is *re-opened*, the handle
is seeded from the stored color via `colorToHue(currentSlotColor)` (line 129) / `colorToHue(stored...)`
(line 180), which reads back ONLY the hue. So any non-vivid color a user lands on cannot round-trip: the
stored override is full-sat/full-value, and the picker can only ever produce full-sat/full-value. This is
internally consistent (lossy in, lossy out) so it won't crash, but it silently constrains the editable
gamut to the rim of the color wheel — a user cannot pick a muted/pastel/dark status or pool color even
though the ColorWheel and the persisted ARGB are capable of it. For status overrides where "color is
yours" is the explicit D-03 promise, this quietly breaks that promise.
**Fix:** If the wheel only exposes hue by design, state that contract explicitly in the KDoc (it
currently reads as if arbitrary colors are pickable). If muted colors should be pickable, carry S/V
through the wheel callback and into `hueToArgbLong`, and seed the handle from the full HSV on re-open.

### WR-03: ThemeEditor status-override picker reads the raw stored Long without the `isValidArgb` sanitize the resolver applies

**File:** `app/src/main/java/works/mees/dinghy/ui/screen/ThemeEditorScreen.kt:178-181`
**Issue:** The status picker seeds its handle from `activeProfile?.poolOverrides?.get(statusSlot.key)`
then `storedArgb?.toComposeColor()`. The resolver path drops an out-of-range ARGB per-entry via
`sanitizeTuple` (`isValidArgb`, ThemePrefs.kt:267), but this UI read bypasses that — a corrupt blob with
a stop key holding `0x7_FFFF_FFFF` is dropped by the resolver (so the app renders the generated color)
yet the editor handle would be positioned from `(0x7FFFFFFF).toInt().toComposeColor()`, i.e. a different
color than what is actually applied. The handle and the rendered status would disagree. Same class of read
exists at line 291/310 (`overrides.containsKey(...)`) but that one only drives an "overridden" dot, so
it's cosmetic. The handle-seed is the more misleading one.
**Fix:** Route the stored-override read through the sanitized tuple
(`activeProfile?.toThemeTuple()?.statusOverrides?.get(statusSlot.key)`) so the editor sees exactly what
the resolver will apply, or fall back to `effective` when the stored value fails `isValidArgb`.

### WR-04: `ConsoleRowView` severity glyph + base text size ignore the active `--fs` text-size setting

**File:** `app/src/main/java/works/mees/dinghy/ui/console/ConsoleRowsAdapter.kt:151, 206`
**Issue:** `ConsoleRowView` hardcodes `textSize = 14f` in `init` and sizes the severity glyph from that
raw `textSize` (`val px = (textSize).toInt()`). The KDoc on `applySeverityGlyph` (line 184-185) claims the
glyph "tracks the S/M/L --fs setting that scales the row textSize the same way" — but nothing in this file
ever multiplies by `fs`. Unlike every Compose surface reviewed (which uses `fsSp(base, t.fs)`), the
console row text and its octagon/triangle glyph are fixed at 14sp regardless of the S/M/L setting. On the
Nexus-7-class floor at arm's length this is exactly the [[dinghy-font-sizes-too-small]] trap, and the
14sp base is already below the documented 15sp metadata floor. The shape-coded safety glyph is
correspondingly undersized.
**Fix:** Thread `fs` into the palette/bind path (the `ConsoleRowPalette` is already pushed from the
Composable, which has `t.fs`) and set `textSize = fsSp(15f, fs) * density`-equivalent, then size the
glyph off the scaled `textSize`. At minimum raise the 14sp base to the 15sp floor.

### WR-05: `effectiveStatusColor` is mode-blind — the editor swatch can show the override color in a mode that ignores it

**File:** `app/src/main/java/works/mees/dinghy/ui/screen/ThemeEditorScreen.kt:314, 521-526`
**Issue:** `StatusSlotSwatch(fill = effectiveStatusColor(t, s), ...)` renders `t.stop`/`t.heat`/`t.go`
straight from the resolved tokens, which IS mode-gated, so the swatch is correct. But the status *picker*
(lines 173-233) lets the user pick and persist a color in Simple/High-Contrast while telling them via
`SubLabel` it "won't show here" — the override IS written (`setActiveStatusOverride` always persists),
and `overrideTakesEffect` (line 183) only controls the copy, not the write. That's defensible (saved for
Colorful), but the `storedArgb` handle seed (WR-03) combined with this means in High-Contrast the user
sees a wheel handle at their saved hue, the swatch behind it showing the forced-RYG color — two different
colors with no visual reconciliation. Not a crash, but a confusing UX state that will read as a bug.
**Fix:** When `!overrideTakesEffect`, either disable the wheel or annotate the swatch with the saved
(but inactive) color so the handle and the preview tell a consistent story.

## Info

### IN-01: Stale KDoc on `BedMeshHeatmapView.OPAQUE_BLACK` — it is the lerp alpha mask, not a "placeholder"

**File:** `app/src/main/java/works/mees/dinghy/render/BedMeshHeatmapView.kt:222-223`
**Issue:** The constant is documented as "Opaque-black placeholder for the pre-`applyTokens` ramp fields
(never painted — see field doc)." That is false: `OPAQUE_BLACK` is the `0xFF000000` alpha mask OR-ed into
every `lerpArgb` result (line 257) and IS painted on every cell. There are no "pre-applyTokens ramp
fields" anymore (the ramp is baked at construction). The comment will mislead anyone touching the lerp.
**Fix:** Reword to "Opaque-alpha (0xFF<<24) mask OR-ed into each interpolated cell color."

### IN-02: `sanitizeTuple` KDoc and `assertFullyUsable` say poolShift range is 0..360, code enforces 0..359

**File:** `app/src/main/java/works/mees/dinghy/theme/ThemePrefs.kt:206`, test `ThemePrefsFallbackTest.kt:34`
**Issue:** `SHIFT_RANGE = 0..359` (correct per WR-04 comment — 360 ≡ 0). But the `sanitizeTuple` KDoc
(ThemePrefs.kt:206) still says "out-of-range poolShift (0..360)" and the test's `assertFullyUsable`
asserts `t.poolShift in 0..360`. The test is weaker than the code (would pass a value of 360 the code
actually rejects, but since the code never emits 360 the assertion never sees it). Doc/test drift only.
**Fix:** Update the KDoc to 0..359 and tighten the test assertion to `0..359`.

### IN-03: `fmt()` (one-decimal mm/°C formatter) is duplicated across four files

**File:** `MoveScreen.kt:595`, `PrintStatusScreen.kt:901`, `TemperatureScreen.kt:470` (and a similar
`fmtDist`)
**Issue:** `private fun fmt(v: Double): String = ((v * 10).roundToInt() / 10.0).toString()` is copy-pasted
verbatim in at least three reviewed files. Behavior is identical; this is maintenance duplication (a
locale/format fix would have to be made in N places). Also `.toString()` on a Double is locale-independent
in Kotlin but will render `"23.0"` not `"23"` — fine here, just noting the repetition.
**Fix:** Hoist to a shared `works.mees.dinghy.theme`/`util` formatter (the project already centralizes
`fsSp` similarly).

### IN-04: `ThemeEditorScreen` "Reset theme?" confirm message has a grammar error

**File:** `app/src/main/java/works/mees/dinghy/ui/screen/ThemeEditorScreen.kt:110`
**Issue:** `"This clears your custom pool colors and randomize back to the default."` — "randomize" should
be "randomization" (or the clause reworded). User-facing copy on a destructive confirm guard.
**Fix:** "This clears your custom pool colors and resets the palette back to the default."

### IN-05: `parseHex` truncates to first 6 hex chars, silently ignoring alpha on 8-digit input

**File:** `app/src/main/java/works/mees/dinghy/ui/screen/ThemeEditorScreen.kt:594-600`
**Issue:** `parseHex` does `s.take(6).toIntOrNull(16)` and forces `0xFF000000` alpha. An 8-digit
`#AARRGGBB` preset would have its first 6 chars (`AARRGG`) parsed as RGB — wrong color, not just dropped
alpha. The current `PRESET_SEEDS` are all 6-digit so this never fires, but the helper is `internal` and
named generically, inviting future 8-digit callers into a silent mis-parse.
**Fix:** Either reject non-6-digit input explicitly or parse the trailing 6 of an 8-digit string. At
minimum, document the 6-digit-only contract.

### IN-06: `OklchRamp.hexToArgb` assumes a 6-char hex and will throw on any other length from `Palette.oklchToHex`

**File:** `app/src/main/java/works/mees/dinghy/theme/OklchRamp.kt:85-91`
**Issue:** `hexToArgb` does `s.substring(0,2)/(2,4)/(4,6)` with no length guard. It relies entirely on
`Palette.oklchToHex` always returning a clean `#rrggbb`. That invariant holds today (golden-tested), and
the ramp bakes at construction so a throw would be a hard fail-fast at startup rather than a per-frame
crash — acceptable. Flagged only because it is an unchecked `substring` with an implicit cross-module
contract; if `oklchToHex` ever returns shorthand or alpha hex, this throws `StringIndexOutOfBounds`
during view construction.
**Fix:** No change required given the golden test; optionally add a `require(s.length >= 6)` for a
clearer failure message.
