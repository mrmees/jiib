<objective>
Wave 1 — the headline fix. Make the in-session klippy-restart re-handshake VISIBLE (emit Syncing/Connected,
D-03), DISCONNECT-DRIVEN (recover off the drop signal the capture identified, not only ready, SC-2), and
SELF-HEALING (on re-handshake failure — or a drop never followed by recovery — force a full reconnect by
closing the REAL socket via the existing supervisor instead of swallowing it forever — the D-01 fallback,
now reached FROM the root cause).

Purpose: This is the bug that froze the live feed until app force-restart (the reason Phase 13 was
promoted). RESEARCH H1 pins it to the silent fire-and-forget `runCatching { runHandshake() }` that swallows
subscribe failure with no retry/escalation, plus recovery gated only on notify_klippy_ready. THE MECHANICAL
TRAP (Codex review, verified against source): `JsonRpcClient.close()` (JsonRpcClient.kt:203) only nulls the
connection and fails pending requests — it does NOT close the websocket; `connectAndServe()` parks on
`closed.await()` (MoonrakerSession.kt:314) which is only completed by a real SocketEvent.Closed (~265) or
the socket flow completing (~270). So escalating by calling `rpc.close()` would NOT unblock the supervisor —
still dead-forever. The escalation MUST close the real `RpcConnection`/OkHttp socket so the socket flow emits
Closed. Every change here is a REUSE of proven plumbing — the same emit()/markStale/seed the socket-death
path uses, RpcConnection.close() the served-then-died teardown already triggers, and the run() supervisor
that demonstrably works on a fresh socket. Inventing new machinery is exactly how the silent re-handshake
became a dead-forever trap.

Output: a modified MoonrakerSession.kt (and, only if the capture dictates a webhooks.state signal, a small
store/reducer edge exposure) where klippy-restart recovery looks identical to a reconnect (Syncing splash →
fresh seed → Connected) and self-heals by closing the real socket on failure. The Wave-0 RED tests turn
GREEN.
</objective>
