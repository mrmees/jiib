<objective>
Build the per-type immediate-dispatch detail pages: add a concrete settle-dispatch mode to `ScrubberPage`
(HIGH-3 — a real API change, not a wiring footnote), a shared scrubber detail (fan %, heater °C, servo °,
output_pin-pwm %, pwm_tool %), the LED page (hue ColorWheel + brightness scrubber + explicit Off, D-12),
and the output_pin page that branches digital→toggle / pwm→scrubber (the toggle is the one new small UI
piece). Every page dispatches immediately on settle (no Apply, no ConfirmGuard) THROUGH the CommandRegistry
catalog (HIGH-2), builds commands from the bare `commandName` (HIGH-1), shows failures as a toast, and
scopes busy to the page.

Purpose: SC-2 (keyboard-free set, confirmed by state flip) + SC-3 (read-only degrades). The staging grammar
is strict: immediate dispatch, NO Apply flow, NO ConfirmGuard even for risky pins/PWM, Off dispatches
immediately, toast feedback, stay-on-page on failure. Three review gates close here: (1) HIGH-3 — ScrubberPage
today hardcodes Cancel/Apply in its gutter (lines 209-247) and only commits on Apply; the staging grammar
needs immediate dispatch on settle with NO Apply, so ScrubberPage MUST gain a settle-dispatch API; (2) HIGH-2
— the established analog (`ExtrusionScreen` lines 91-105) dispatches through registered `CommandSpec`s via
`dispatchCommand(CommandRegistry.<spec>, args)`, so the output detail pages dispatch the same way, NOT raw
`GCODE_SCRIPT`; (3) HIGH-1 — commands are built from `descriptor.commandName` (bare), never `objectKey`.
ColorWheel is hue-only, so the LED page pairs it with a brightness scrubber + the 19-03 hsvToRgb helper
(fixed saturation v1).
Output: the ScrubberPage settle mode + the detail pages + the new toggle control + LED/settle command tests
+ a detail preview matrix.
</objective>
