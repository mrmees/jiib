Wire the prompt feature into the live shell, document the D-03 carve-out in the UI LAW, and prove the
mandatory mock-vs-reality behaviors on real hardware. Construct the `PromptEngine` in `AppShell`
(`remember(store)`, dispatcher events from the spine), hoist the `PromptDialog` overlay OUTSIDE

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Button press -> printer gcode execution | A prompt button dispatches arbitrary macro-authored gcode (by design); the dispatcher is the choke point |
| Local disconnect/Back -> other connected clients | A local teardown must not broadcast prompt_end (cross-client side effect) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-12-17 | DoS (cross-client) | AppShell disconnect / BackHandler | mitigate | The engine's disconnect path is a LOCAL reducer reset (no dispatch) — proven host-side in 12-03 AND on-device-gated here (Task 2 step 3). The user-tapped Close + system Back DO dispatch prompt_end (explicit user dismissal, spec-sanctioned); disconnect/process-death do NOT (D-10). |
| T-12-18 | Elevation (arbitrary gcode) | button dispatch | accept (by design) | Button gcode is intentional macro-authored execution (SPEC Security Model); Dinghy does NOT sandbox or add a ConfirmGuard (D-11) — the author signals danger via the `error` style (-> red). This is the documented, accepted protocol design. |
| T-12-19 | Secrets in logs | rejection toast | mitigate (inherited) | Button-rejection toasts are built from `CommandDispatcher`'s already-redacted `DispatchEvent.Failure.message` (no `?token=`), never raw exception text. |
| T-12-SC | Tampering | npm/pip/cargo installs | accept | No package installs in this phase (RESEARCH § Package Legitimacy Audit: zero new dependencies; coil-svg deferred to alt-text fallback unless a verified pinned artifact is added in 12-04). slopcheck N/A. |
