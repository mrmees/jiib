# Phase 12 — UI Design Contract

> Visual and interaction contract for the **PromptDialog** full-screen overlay that renders the
> Macro Prompt Protocol v1. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Scope of this contract:** ONLY the render surface — the full-screen PromptDialog overlay and its
> sub-components (title, markup/text/image content items, content button rows + groups, footer action
> bar, close control) and their states. The parser/reducer + fixture conformance (the bulk of the
> phase) is a non-visual concern owned by `SPEC.md` + `fixtures/fixtures.json` and is NOT specced here.
>
> **Source of truth precedence:** the app-wide UI LAW (`docs/ui_design/CLAUDE.md`, `LAYOUT.md`,
> `THEMING.md`) governs ALL dialog chrome. This file is a *phase application* of that LAW — it does not
> re-derive tokens, it consumes them. The one deliberate exception (author hex in markup runs) is
> called out explicitly below and is itself being added to the LAW (D-03).

## Design System

| Property | Value |
|----------|-------|
| Tool | none (native Android Jetpack Compose — shadcn N/A) |
| Preset | not applicable |
| Component library | Material 3 (Compose) + project `designsystem/` primitives (OutlinedControl, ConfirmGuard, SeverityToast) |
| Icon library | Material Symbols (`MaterialSymbol`) |
| Font | Geist (UI text + markup runs) / Geist Mono (tabular numeric data only) |

**Render policy (LOCKED, do not re-litigate):**
- **Always full-screen overlay** (D-05). Rendered OUTSIDE the `when(dest)` block in `ui/shell/AppShell.kt`
  via hoisted state (`if (promptActive) { PromptDialog(...) }`), exactly like `MacroExecutionPopup` — it
  is an overlay, NOT a `Dest`.
- **`prompt_size` is parsed + tracked in normalized state but the renderer CLAMPS to full-screen** (D-06).
  This contract therefore defines NO size-based envelope, max-width ladder, or modal sizing. The
  Fluidd px max-width table in `SPEC.md` is illustrative only and explicitly ignored at render.
- **Responsive Focus/Field/Gutter + portrait & landscape** (D-07). The overlay obeys `LAYOUT.md`.
- **One-shot show/hide only.** No continuous/looping/"breathing" animation (Adreno-320 fill-rate floor).
  A cheap one-shot fade or slide on show/dismiss is permitted; nothing that runs while idle.

## Layout Contract — PromptDialog regions

The overlay maps onto the Focus / Field / Gutter grammar (`LAYOUT.md`). The protocol's structure maps
to regions as follows:

| Protocol element | Region | Behavior |
|------------------|--------|----------|
| `prompt_begin <title>` | **header band** (above Focus/Field) | Title text, full content-area width, left-anchored. Geist SemiBold. Always present (a prompt with no title shows an empty-but-reserved band — see Degenerate States). |
| `prompt_text` / `prompt_markup` / `prompt_image` content items, rows, button groups, content buttons | **Field** (scrollable) | The content flow. Vertically scrollable when it overflows (`verticalScroll`), because content count is author-controlled and unbounded. **Items default to CENTERED horizontal alignment** (spec default); `prompt_align left/right` overrides per top-level item. |
| `prompt_footer_button`s | **Gutter** (action bar) | The footer action bar — a visually separated row at the bottom, full content-area width, equal-width cells, source order preserved. **The close control lives here too** (see Close Control). |

**Region presence rules:**
- There is **no Focus region** for prompts in the general case — prompt content is heterogeneous and
  author-driven, so it all lives in the scrollable Field. (A prompt that is a *single* `prompt_image`
  with no other content MAY render that image as a centered Focus square per `LAYOUT.md §2`; this is an
  allowed optimization, not a requirement. Default: image is a Field content item bounded per below.)
- The **Gutter (footer action bar) is always present** because it always holds at least the close
  control, even when the macro declares zero footer buttons. This satisfies `LAYOUT.md`'s "there is
  always an exit" rule — the overlay must never trap the user.
- Because the Field is a finger-scrollable list, the **swipe-up App Drawer is suppressed while the
  prompt is visible** (`LAYOUT.md` "Scroll Field ⇒ no swipe-up drawer"). The overlay sits above the
  shell anyway, but the suppression must be explicit so a content scroll never triggers nav.

**Orientation:**
- **Portrait:** header band → scrollable Field → footer action bar, stacked full content-area width.
  Footer bar may wrap to two equal-height rows if footer-button + close-control count exceeds a
  comfortable single-row cell width.
- **Landscape:** header band full width on top; the scrollable content Field spans the full content
  width (there is no Focus to pair it with), footer action bar full width below on the shared grid.
- All dimensions are ratio/`fr`/`aspect-ratio`/container-relative — **no hardcoded region px**
  (`LAYOUT.md §3`). Permitted fixed values: 2px outline hairlines, the 64dp touch floor, the `--fs` step.

## Spacing Scale

Declared values — all on the standard set {4, 8, 16, 24, 32, 48, 64}:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4dp | inline icon gaps inside a row cell |
| sm | 8dp | tight intra-component gaps — inner button padding, gap between footer buttons |
| lg | 16dp | **default gap** — between content items; overlay outer padding (matches `MacroExecutionPopup` `.padding(16.dp)`); gap between header / Field / footer bands |
| xl | 24dp | major vertical break between the content Field and the footer action bar |

**Touch-target floor (non-negotiable):** every interactive element — content button, footer button,
close control — is **≥64dp tall** (`docs/ui_design/CLAUDE.md`; matches `OutlinedControl` / `PopupControl`).
Content buttons fill their cell width; footer buttons are sized by the action bar (D-12).

Exceptions: none beyond the LAW's permitted fixed values (hairline, touch floor, `--fs` step).

## Typography

Use the established `fsSp(baseSp, t.fs)` scale — **never a bare sp**. Mind the recurring
**fonts-too-small** lesson: floor is 15sp for metadata, body 17–18sp, titles 22–28sp.

Four distinct sizes only — `15 / 18 / 22 / 28` — exactly the protocol-mandated PromptMarkup
`<size:small|normal|large|x-large>` ladder. The dialog title reuses the 28sp display tier (it does
NOT introduce a 5th size).

| Role | Base size (`fsSp(_, t.fs)`) | Font | Weight | Notes |
|------|------------------------------|------|--------|-------|
| Dialog title (`prompt_begin`) | **28sp** | Geist | SemiBold | Author text, not a filename → Geist, NOT Mono. **Shares the 28sp display-tier value with `<size:x-large>`** (no extra size introduced); reads clearly above the 22sp tier and matches the `MacroExecutionPopup` 28sp title anchor. `maxLines = 3`, ellipsis. |
| Markup / text content body | **18sp** | Geist | Regular (400) base | The PromptMarkup default. `<b>` lifts to SemiBold (600); `<size:...>` overrides per the size ladder below. Line-height ~1.4 for readable multi-line prose. |
| Content button label | **18sp** | Geist | SemiBold | Plain text only (button-label markup is NOT v1). `maxLines = 2`, ellipsis. |
| Footer button label | **18sp** | Geist | SemiBold | Same as content buttons. |
| Image alt-text fallback (failed/rejected image) | **15sp** | Geist | Regular | Rendered as plain centered text when an image fails to load or is policy-rejected (D-07 / SPEC images). |

**PromptMarkup `<size:...>` ladder** — the four protocol sizes ARE the four declared sizes, mapped onto
the body base via `fsSp`:

| Markup size | Base sp (before `fs`) | Relationship to body |
|-------------|------------------------|----------------------|
| `small` | 15sp | floor — never below the 15sp metadata floor even at `--fs` S |
| `normal` | 18sp | == body default |
| `large` | 22sp | title-tier |
| `x-large` | 28sp | display-tier (focus-tier emphasis) — **also the dialog-title size** |

> Weight policy: the LAW prefers exactly two weights (Regular 400 + SemiBold 600). PromptMarkup `<b>`
> uses SemiBold; `<i>` uses italic style (a font *style*, not a third weight); `<u>` uses underline
> decoration. No bold-italic-heavy combination introduces a third weight.

## Color

ALL dialog **chrome** routes through semantic role tokens (`THEMING.md`) — never a raw color. The ONE
carve-out is author hex inside markup *text runs* (D-03/D-04), bounded precisely below.

### Chrome (semantic tokens only — the 60/30/10 discipline)

| Role | Token | Usage in PromptDialog |
|------|-------|------------------------|
| Dominant (60%) | `--bg` (`t.bg`) | the full-screen overlay backdrop (opaque — `MacroExecutionPopup` precedent: `Box(...).background(t.bg)`). The overlay fully occludes the screen beneath; it is a modal surface, not a scrim. |
| Secondary (30%) | `--surface` / `--surface-2` (`t.surface`, `t.surface2`) | optional content-item card backgrounds, the footer action-bar band, disabled-control fills | 
| Text | `--text` / `--text-2` / `--text-3` (`t.text`, `t.text2`, `t.text3`) | title (`text`), body default (`text`), captions/alt-text (`text2`), disabled label (`text3`) |
| Control bound | `--outline` (`t.outline`) | the 2px outline + glow on every interactive control (the `OutlinedControl` language) |
| Accent (10%) | `--accent` / `--accent-line` (`t.accent`, `t.accentLine`) | reserved for `primary`-style + `info`-style buttons (see button mapping) and the close control — NOT applied to all controls |
| Hairline | `--hair` (`t.hair`) | disabled-control outline; band separators |

**Accent reserved for:** `primary`-style content/footer buttons, the close control, and (as a brighter
text tint `accent2`) `info`-style buttons. Accent is NEVER the default control color — `secondary` (the
protocol default style) is the neutral `--outline`, so an undecorated prompt is mostly chrome-neutral.

### The 6 protocol styles → Dinghy button colors (D-11)

The protocol's 6 styles are **author-chosen emphasis tiers**, not Dinghy's safety-based `Intent` system.
We map them to the closest token while preserving the LAW's "color is meaningful" rule. Because the
protocol has 6 buttons and `designsystem/control/Intent` has 5, **`info` is the one style that needs a
color not already in `Intent`** — it resolves to the brighter accent text tint (`accent2`) to read as
distinct-but-related to `primary`. Implement via a small style→color resolver in the PromptDialog
(NOT by adding a 6th `Intent` enum member — `Intent` is the safety vocabulary and must stay 5).

| Protocol style | Dinghy token (outline + label tint) | Rationale |
|----------------|--------------------------------------|-----------|
| `primary` | `--accent` / `--accent-line` | the macro's main action; matches Dinghy's "ordinary physical command" accent |
| `secondary` (DEFAULT) | `--outline` (neutral) | the unstyled default; reads as plain chrome — the most common button |
| `info` | `--accent-2` (brighter accent tint) | informational/secondary-prominent; distinct from primary without a new safety color |
| `warning` | `--heat` (amber) | proceed-at-peril; aligns with Dinghy's Warn/amber |
| `error` | `--stop` (red) | destructive/dangerous; aligns with Dinghy's Danger/red |
| `success` | `--go` (green) | accept/positive; aligns with Dinghy's Go/green |

> Buttons do **NOT** auto-close (D-11). Only `action:prompt_end` (emitted by a button's gcode, OR by the
> close control) closes the prompt. A button press dispatches its gcode via the shared
> `CommandDispatcher` (`printer.gcode.script`, busy-keyed, debounced, redacted-failure→`SeverityToast`).
> There is intentionally **no ConfirmGuard** layered on a prompt button — the macro author owns the
> action semantics, exactly as `MacroExecutionPopup`'s Execute is its own gate.

### The markup hex carve-out (D-03 — bounded precisely)

ONLY macro-authored PromptMarkup **text runs** honor author hex:
- `<color:#rrggbb>` → that exact foreground color on the run's `AnnotatedString` span.
- `<bgcolor:#rrggbb>` → that exact background color on the inline run (inline span, never a layout block).
- Invalid hex (not exactly 6 hex digits after `#`) → **ignored, inner text preserved** at the default
  `--text` token color (SPEC: "invalid color values are ignored while preserving inner text").

This is content DATA, not chrome — precedent is the Spoolman spool-color detail border already rendering
real hex. **Everything that is NOT a markup text run still uses tokens:** the overlay background, the
title, plain `prompt_text`, all button outlines/labels/fills, the footer bar, the close control, card
backgrounds, separators. The carve-out is documented in `docs/ui_design/CLAUDE.md` + `THEMING.md` as part
of this phase so it does not read as a token-purity violation to the auditor.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--bg` token | full-screen overlay backdrop |
| Secondary (30%) | `--surface` / `--surface-2` tokens | footer bar, optional content cards, disabled fills |
| Accent (10%) | `--accent` / `--accent-2` tokens | `primary`/`info` buttons + close control ONLY |
| Destructive | `--stop` token | `error`-style buttons ONLY |
| **Carve-out (data, not chrome)** | author `#rrggbb` from `<color>`/`<bgcolor>` | markup text runs ONLY (D-03) |

## Image bounding (Adreno-320 fill-rate floor — D-07)

`prompt_image config/...|alt|scale` content items MUST be bounded hard; never rendered at intrinsic size.

- **Decode + downscale with Coil 3**, reusing the Phase-10 / Files downscale discipline (`inSampleSize`/
  request size tied to the target cell, never full-res). A full-res decode OOM/janks the 2GB Adreno-320.
- **Fit, never crop** (`ContentScale.Fit`) — `LAYOUT.md` content-image rule + SPEC `object-fit: contain`.
  The whole image is visible, centered/letterboxed in its bounding box; both width and height bounded.
- **Bounding box = a square tied to the dialog content width** (SPEC convention ≈ contentWidth / 3),
  then multiplied by the parsed `scale` (clamped: invalid/non-finite/≤0 → 1.0). Because the renderer is
  always full-screen, the base tracks the full-screen content width (the SPEC `full-screen` ≈ 33vw row).
- **Failure / rejected path / unsupported format:** render the alt text as plain centered 15sp Geist
  `--text-2` (SPEC). If no alt text, omit the item silently. A failed image **never** blocks the rest of
  the prompt from rendering.
- **Path safety is enforced before load** (SPEC valid-path rules: `config/...`, forward slashes, no `/`
  `~` leading, no empty/`.`/`..` segments, no `:` in a segment). A rejected path → alt-text fallback.
- SVGs render as image assets only (no markup injection); PNG/JPEG/SVG are the required formats.

## Row & Button-Group layout (equal-width cells — D-12)

- `prompt_row_*` and `prompt_button_group_*` render their children as **equal-width cells, content
  centered within each cell** (SPEC equal-width-cells convention; D-12). Implement with a Compose `Row`
  whose children each take `Modifier.weight(1f)`.
- A **content button inside any container fills its equal-width cell** (`Modifier.fillMaxWidth()` within
  the weighted cell); never sized to its label text.
- A **standalone (top-level) content button fills the full content width** of its row in the Field.
- Rows may contain text / markup / image / inline button children, laid out in source order.
- Rows and button groups are **never nested** (SPEC); a malformed nested/unmatched container degrades
  deterministically per the reducer — the renderer just draws whatever normalized items it receives, so
  the renderer needs no special nesting logic beyond "a row/group is a weighted Row of cells."

## Close Control (D-11)

- A **dedicated close control is always present** in the footer action bar (regardless of declared
  footer buttons), so the user can always dismiss the overlay. It is the "always an exit" guarantee.
- Tapping it emits `action:prompt_end` — i.e. it dispatches `RESPOND TYPE=command MSG="action:prompt_end"`
  via the same gcode path a footer button would (NOT a local-only teardown). Per SPEC, `prompt_end` is
  broadcast and closes the prompt on every connected client; the close control is an *explicit user
  action*, which is exactly what the spec sanctions for dismissal.
- Visual: an `--accent` outlined icon-led control (e.g. a `close` Material Symbol + "Close" label).
  It is distinct from any author footer button. ≥64dp touch target.
- **Local teardown ≠ prompt_end:** if the overlay is closed because Dinghy itself is going away
  (process death) or because of **disconnect (D-10)**, that is a LOCAL close and must **NOT** emit
  `prompt_end` (it would wrongly close the prompt on other clients). Only the user-tapped close control
  and author button gcode emit `prompt_end`.

## Empty / Degenerate States (graceful tolerance is the whole point)

The protocol guarantees graceful degradation; the renderer must visibly honor it.

| State | Render |
|-------|--------|
| **Prompt with no content items** (only `prompt_begin` + `prompt_show`) | Title band + an empty Field + footer bar with the close control. Field shows a quiet centered 15sp `--text-2` placeholder: **"This prompt has no content."** Never a blank crash. |
| **Prompt with no title** (empty `prompt_begin` arg) | Title band renders empty/reserved (no placeholder text — an absent title is valid). Content + footer still render. |
| **No footer buttons declared** | Footer action bar still renders, containing only the close control. |
| **No content buttons, no footer buttons** (read-only/notice prompt) | Content renders; footer bar holds only the close control — user dismisses by closing. |
| **Unknown command / unknown markup tag / invalid color / invalid size** | Reducer strips/ignores per SPEC; the renderer simply never receives a malformed item. Unknown tags → inner text preserved at `--text`. Renderer needs no error UI for these — they are normalized away upstream. |
| **Image fails / rejected path / unsupported** | Alt text as plain centered 15sp `--text-2`; or item omitted if no alt. Rest of prompt unaffected. |
| **Disconnect while prompt visible (D-10)** | Overlay closes locally (NO `prompt_end` emitted), pending `prompt_target`/`prompt_size` + any open container cleared. The shell's reconnect Splash (Phase-13 routing) takes over the screen. On reconnect, **no replay** this phase — wait for the next `prompt_*` sequence. |
| **Button gcode rejected by printer** | The dispatch surfaces a `SeverityToast` (Error) over the overlay (redacted message from `CommandDispatcher`); the prompt stays open (buttons don't auto-close). |
| **Button dispatch in flight** | The pressed button shows the busy/in-flight state (debounced via `CommandDispatcher` busy key), consistent with `MacroExecutionPopup`'s running state. |

## Copywriting Contract

All copy is terse, kiosk-legible at arm's length, sentence case.

| Element | Copy |
|---------|------|
| Primary CTA | (none fixed — content/footer button labels are macro-AUTHORED plain text, rendered verbatim. Dinghy supplies NO default labels except the close control.) |
| Close control label | **Close** (with `close` Material Symbol) |
| Empty content placeholder | **This prompt has no content.** |
| Empty content body / next step | (single line; no secondary line needed — the close control is the obvious exit) |
| Button-rejected error (toast) | **{button gcode} was rejected: {redacted printer message}** (mirrors `MacroExecutionPopup`'s "{name} was rejected: …") |
| In-flight info (toast) | **Sending… waiting for the printer.** |
| Image-failed fallback | the macro's alt text, verbatim (Dinghy supplies no copy; if absent, the item is omitted) |
| Destructive confirmation | **none** — prompt buttons never get a ConfirmGuard (D-11); the macro author owns action safety. The close control is non-destructive (green-adjacent semantics: closing a prompt changes no printer state, but it dispatches `prompt_end`, so it reads as accent, not red). |

> Note on the destructive-action rule: this phase introduces **no Dinghy-authored destructive action**.
> A macro *button* may run dangerous gcode, but its danger is signalled by the author choosing the
> `error` style (→ `--stop` red); Dinghy does not second-guess it with a confirmation gate.
