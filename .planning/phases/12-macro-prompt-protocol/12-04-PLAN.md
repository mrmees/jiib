<objective>
Build the full-screen `PromptDialog` overlay and its sub-components from the existing design-system
primitives: the markup AST -> `AnnotatedString` builder (the one genuinely-new Compose piece, with the
D-03 author-hex carve-out), the 6-style -> token resolver, content/footer buttons + close control, the
equal-width row/group cell layout, the empty/degenerate states, and the Coil-bounded image item.

Purpose: This is the render contract from `12-UI-SPEC.md` — a reuse-heavy assembly following the
`MacroExecutionPopup` overlay precedent. All chrome routes through semantic tokens; the ONE carve-out is
author hex inside markup text runs (data, not chrome — precedent: Spoolman spool colors). Images are
bounded HARD for the Adreno-320 fill-rate floor. PROMPT-02 (render dialog, buttons fire gcode — the gcode
WIRING is in 12-05; this plan builds the rendering + the onButton/onClose callbacks).

Output: `ui/prompt/PromptDialog.kt` + sub-components + the style-resolver unit test. The AppShell hoist +
the actual dispatch wiring is 12-05. This plan keeps the overlay parameter-driven (takes a `PromptView` +
`onButton(buttonIndex)` + `onFooterButton(footerIndex)` + `onClose()` + an `httpBase`), so it composes
standalone in a preview/UI test.

BUTTON-INDEX CONTRACT (the load-bearing cross-plan agreement — implement EXACTLY, also in 12-05):
The dialog walks `view.items` DEPTH-FIRST, descending into `row`/`button_group` children, visiting CONTENT
BUTTONS ONLY (text/markup/image items and the containers themselves are skipped), assigning each button a
stable sequential `buttonIndex` 0,1,2,… in that depth-first order. A content button's `onClick` fires
`onButton(buttonIndex)`. The SAME ordering is produced by the ONE shared helper
`fun PromptView.flattenContentButtons(): List<PromptButton>` in `ui/prompt/PromptButtonFlatten.kt` — the
renderer keys its click wiring off it AND 12-05's AppShell resolves the gcode by `flattenContentButtons()[buttonIndex]`.
FOOTER buttons are a SEPARATE sequence: `view.footer_buttons[footerIndex]` fired via `onFooterButton(footerIndex)`
(footer buttons are NOT in flattenContentButtons and NOT depth-first interleaved with content). The CLOSE
control is in NEITHER list — it has its own `onClose()` and emits `prompt_end`. This is the silent-runtime-defect
guard: a flat `view.items` index would dispatch the wrong gcode for a button nested in a row/button_group.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Macro-authored markup -> rendered text | PromptMarkup is hostile/author content; must render as neutral spans only, never as executable/HTML |
| Macro-authored image path -> Coil HTTP load | The `config/...` path reaches the loader; resource exhaustion + traversal are the risks |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-12-13 | Tampering/Elevation (injection) | PromptMarkupText | mitigate | Markup renders ONLY as Compose `AnnotatedString`/`SpanStyle` — never HTML/Pango/WebView, no script/link/CSS surface. Author hex is a `Color` value on a span, not executable. (V5 injection.) |
| T-12-14 | Information Disclosure | PromptImageItem | mitigate | Only `config/...` paths (vetted by 12-01 `isValidImagePath`) reach `AsyncImage`; a rejected path never gets here (it became alt-text upstream). No path is built from un-vetted segments. (V5 path traversal.) |
| T-12-15 | DoS (resource exhaustion) | PromptImageItem / row cells | mitigate | Hard Coil bounding (`ContentScale.Fit`, bounded square, request size tied to the cell, inSampleSize discipline) — never intrinsic decode (OOM/jank on 2GB Adreno-320). Equal-width `weight(1f)` cells bound row over-draw. One-shot show/hide only — no continuous animation (Adreno fill-rate floor). |
| T-12-16 | DoS (unbounded content) | PromptDialog Field | mitigate | The Field is a `verticalScroll` column — unbounded author content count scrolls rather than overflowing; the close control is always present so the user can never be trapped. |
</threat_model>
