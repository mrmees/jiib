      LAW and the code agree): `nTarget = round(contentMinDim / 41dp).coerceIn(5,7)`,
      `nMaxFit = (contentMinDim / 64dp).toInt().coerceAtLeast(5)`, `N = min(nTarget, nMaxFit)`, `U = contentMinDim / N`.
      State plainly WHY this form: applying the 64dp floor AFTER picking N (the naive `(dim/N).coerceAtLeast(64dp)`)
      OVERFLOWS small phones (360dp → N=7 → 7×64=448dp > 360dp); reducing N first guarantees `N×U == contentMinDim`
      (no dead remainder, no overflow) while U stays ≥64dp on the phone floor. Derived from the LANDSCAPE-constrained
      short edge `minOf(width,height)` and held constant through rotation; portrait shows more units (scrolls);
      the "must survive at 5 units" worst-case rule; settings exempt (C6).
      Add a clarifying note resolving the "DPI-derived" wording: `U` is **dp-derived** — the 41dp short-edge target.
      Because Compose `Dp` is density-independent, that dp target IS the density-correct ("DPI-derived") anchor;
      there is no separate runtime DPI/density parameter. The `U_target ≈ dpi/2.4` figure in RESEARCH is the
      derivation of WHY 41dp, not a runtime input.
    - §"Content vs controls — fill convention" — list items translucent (transparent fill, outline only =
      content), buttons/tiles/cards/action-bars filled (surface shade = controls); selection/active layers accent;
      NO group-label words (separation by outline + fill shade + accent).
    - §"Foot-of-list pattern" — any screen with a primary list pins its actions to the foot of that list
      (the FootButtonBar; Spoolman's 3-button bottom is the prototype); 1U row.
    - §"Floating e-stop" — overlay, top-left of Focus, shown on every screen but ONLY when printing; decoupled
      from layout flow.
    Note that the Kotlin `ScreenScaffold.kt` KEEPS its optional `gutter` slot (backward-compatible for
    pre-redesign screens) even though the doc grammar no longer names it a first-class region.
    NO fenced Kotlin implementations — this is prose design law.
