# Phase 15.2: Theme Conformance Sweep & Settings IA - Research

**Researched:** 2026-06-05
**Domain:** Android/Kotlin Compose+Views theme conformance audit + App-Drawer information architecture + a transient app-wide theme-override dev tool
**Confidence:** HIGH (this is an internal-codebase phase — every load-bearing claim is grepped/read from the repo, not from external docs)

## Summary

This phase has two halves and the research confirms the CONTEXT framing on both, with one important correction to the audit scope.

**Half 1 (conformance sweep):** The token-purity dimension is even healthier than CONTEXT claimed — across the whole `ui/**` + `render/**` tree there are exactly **4 raw `Color(0x…)` literals in 3 files**, all sanctioned data/swatch cases (PromptMarkup carve-out doc-comment, two Settings/SpoolPicker swatch palettes). There is **zero `MaterialTheme.colorScheme` usage** and **near-total `fsSp` discipline** (every `fontSize` traced routes through `fsSp(...)`). So token-purity and fsSp are *verification*, not refactor. **The real weight is the button-intent dimension, and specifically the Back-button sweep** — I confirmed by grep that Back is rendered with *four different intents across screens* today (`Danger`/red on Extrude/Spool/Webcam, `Go`/green on Temperature, `Neutral` on Files/Move). The new LAW (15.1 D-10) makes Back **Neutral app-wide** with a consistent gutter position. That, plus shape-status conformance and FFG/≥64px spot-checks, is the bulk of the sweep.

**Half 2 (IA + cycler widgets):** The architecture supports all of it cleanly. There is exactly **one production `ThemeResolver`** (`AppContainer.themeResolver`), continuously fed by `seedTheme(scope)` which collects the active profile's persisted theme tuple and calls `resolver.apply(...)`. Both toolkits read this one resolver: Compose via `DinghyTheme → LocalTokens`, Views via `applyTokens(t)` pushed through `GraphViewHost`/`BedMeshHeatmapHost`. The cycler's "transient global apply" is therefore a **single, well-defined override layer in front of `ThemeResolver.tokens`** — and the `GalleryScreen` dev surface already demonstrates the mechanic (it calls `resolver.setMode/setDark/setFs` directly). The IA dissolve is additive: extend the `Dest` enum + `DRAWER_TILES` list + the `when(dest)` in `AppShell`, split `SettingsScreen` content across the four new destinations.

**Primary recommendation:** Build the cycler as an **override `StateFlow<ThemeTuple?>` owned by `AppContainer`** that `DinghyTheme` resolves *ahead of* the persisted resolver, never touching the persist path. Do the IA as a 4-value extension of `Dest`/`DRAWER_TILES`. Sequence per D-09: cycler widgets first, then guided 5-10-screen review (criteria harden into THEMING.md), then the AUDIT.md scorecard app-wide, then fix — Back-intent sweep being the single largest fix bucket.

### Pattern 1: Override-ahead-of-persisted (transient global theme)
**What:** A `MutableStateFlow<ThemeTuple?>` on `AppContainer`. `null` = "no override, use the real persisted theme." A non-null tuple = "render the whole app in this combo right now." `DinghyTheme` and every Views `*Host` collect a **derived** `effectiveTokens` flow that picks override-or-persisted.
**When to use:** The D-06/D-07/D-08 cycler. NEVER for a real user theme change (that still goes through `setActive*` → `writeScope` → persist).
**Why this over alternatives:**
- *Rejected: mutate `AppContainer.themeResolver` directly (the GalleryScreen mechanic).* In Gallery there is no persistence collector racing it. In production, `seedTheme`'s collector re-emits `resolver.apply(persistedTuple)` on any profile/theme change, which would **fight** the cycler's `setMode`/`setDark` and snap the theme back mid-sweep. Mutating the live resolver also has no clean "restore" — you'd have to re-read and re-apply the persisted tuple, racing the same collector. The override layer is strictly cleaner: dismiss = set `override = null`, the persisted resolver was never touched, the app snaps back deterministically.
- *Rejected: a second `DinghyTheme` boundary wrapping the cycled subtree only.* Fails the D-08 requirement that the override apply to the WHOLE live app (navigate anywhere, every screen renders it) and would not reach the Views surfaces hosted by the existing single boundary.

**Generation note (important):** the override tuple still needs to become baked `ThemeTokens`. Do NOT call `themeResolver.setMode()` etc. (that mutates the live persisted resolver). Instead generate the override tokens via either (a) a dedicated *second* throwaway `ThemeResolver` instance the container holds for previews, or (b) a direct `Palette.generate(...) → TokenBridge.build(...)` call (the same path `ThemeResolver.compute()` uses — see `theme/ThemeResolver.kt:152-170`). Option (a) reuses the proven fail-safe try/catch; prefer it. [VERIFIED: read ThemeResolver.kt:143-178, AppContainer.kt:320-345]

### Pattern 2: Cycler combos use the user's REAL seed (D-06)
The style cycler steps `{dark,light} × {Colorful, Simple, HighContrast}` (6 combos) but keeps the **user's current accent/seed** — so it tests the real generated themes, not a demo palette. Concretely: read the active profile's persisted `seedHex`/`poolShift`/`poolOverrides`/`maxItems` (off `AppContainer.activeProfile`), and only override `dark` + `paletteMode` (style cycler) or `fsChoice` (size cycler). The size cycler is independent (D-07): it overrides only `fs`. Two independent override axes can be modeled as one `ThemeTuple?` override whose non-overridden fields fall through to the active profile's persisted values.

### Pattern 3: Floating overlay above all routes (AppShell, not a window overlay)
**What:** Render the two cycler widgets as a Compose overlay `Box` inside `AppShell`'s `BoxWithConstraints`, aligned to a corner, drawn AFTER `when(dest)` and the other overlays — exactly like `MacroExecutionPopup`/`ScanSurface`/`PromptDialog` are (`AppShell.kt:607-694`).
**Why this over a system `TYPE_APPLICATION_OVERLAY` window:** A real window overlay needs `SYSTEM_ALERT_WINDOW` permission (a scary install-time/runtime grant, and overkill for an in-app dev tool). The app already floats full-screen overlays over every `Dest` via in-AppShell Boxes; the cycler is the same pattern, gated on the dev-enable boolean. Draggable position (Claude's-discretion) via `Modifier.offset{}` + `detectDragGestures` (precedent exists in `designsystem/ScrubberPage.kt`, `ColorWheel.kt`). **Adreno-320 constraint:** static only — NO continuous/looping animation on the widget (D-13/CLAUDE.md motion law). A one-shot tap ripple is fine; a pulsing glow is not.

### Pattern 4: Lean-router IA extension (NOT Navigation-Compose)
**What:** The IA dissolve is additive to the existing `enum class Dest` + `DRAWER_TILES` list + `when(dest)` block. Add `Dest.Printers` (or reuse `Dest.Devices` renamed), `Dest.Theme`, `Dest.About`; keep `Dest.Settings`. Each is one `DrawerTileSpec` and one `when(dest)` arm.
**Why:** The shell deliberately has **no `androidx.navigation` dependency** (`AppShell.kt:94-97`, `TopRoute.kt`). Adding a 4th/5th destination is a one-line addition by design — do not introduce Nav-Compose now.
**Back-stack landmine:** `ShellNavState.navigateTo` pushes the current dest unless target is `PrintStatus` (which clears the stack). The four IA destinations are normal pushes — no special handling needed. BUT note `AppShell.kt:431` lists swipe-suppressed dests (`Dest.Devices` is in that set because Devices scrolls). If `Printers` is the renamed Devices it stays suppressed; `Theme`/`Settings`/`About` are FFG-exempt keyboard surfaces and likely scroll too → add them to the swipe-suppress set and give each an explicit Back in its layout (the existing rule for scrollable Fields).

### Anti-Patterns to Avoid
- **Routing the cycler through `setActive*`/`writeScope`/`mutateActive`.** That persists — the opposite of the requirement. Honor `[[dinghy-compose-write-scope-cancellation]]`: the cycler writes NOTHING durable; the only persisted thing is the dev-enable boolean (a deliberate, debounced About toggle).
- **A debug-only `BuildConfig.DEBUG` gate for the cycler.** The owner sideloads RELEASE APKs to flox; a `BuildConfig.DEBUG` gate would hide the tool exactly where it's needed (D-08). Gate on a runtime persisted boolean instead.
- **Re-litigating semantics.** 15.2 verifies conformance to 15.1's locked pool→role/shape/N-series/Back-neutral decisions. Do not re-derive them; THEMING.md is the standard.
- **Mass "fixing" the sanctioned raw colors.** PromptMarkup author-hex, Spoolman/SpoolPicker filament swatches, and the Settings/ThemeEditor theme swatches are DATA, not chrome — explicitly carved out by THEMING.md. The audit treats them as conformant.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Whole-app theme flip | A per-screen "preview mode" prop threaded through every screen | One override `StateFlow` in front of the single `DinghyTheme`/`*Host` token source | The single-source/two-consumer shape means one `combine` flips everything; threading a prop touches 30 files |
| Override token generation | A hand-mapped "swap these colors" function | `Palette.generate → TokenBridge.build` (the resolver's own `compute()` path) | The bake/fail-safe/mode-gating logic already exists and is golden-tested; reusing it keeps the override bit-identical to a real theme |
| Floating overlay window | A `WindowManager` `TYPE_APPLICATION_OVERLAY` | An in-`AppShell` Compose overlay `Box` (the MacroPopup/ScanSurface/PromptDialog pattern) | Avoids `SYSTEM_ALERT_WINDOW` permission; matches existing overlay grammar; flips with the same tokens |
| 4-tile routing | A Navigation-Compose graph | Extend `Dest` enum + `DRAWER_TILES` + `when(dest)` | The shell is deliberately Nav-Compose-free (lean router, D-05); one-line additions by design |
| Per-profile toggle persistence | A new DataStore file/store | New fields on `Profile` + `mutateActiveProfile{}` | The per-profile theme tuple already persists this exact way (`Profile.kt:64-77`, `AppContainer.mutateActiveProfile`) |

**Key insight:** Almost every "build" instinct here is already solved one layer down. The substrate was explicitly designed (Phases 14/15) as "extend not rewrite," and the conformance sweep is mostly *deleting* divergence (wrong Back intents), not adding mechanism.

## Common Pitfalls

### Pitfall 1: The persistence collector fights the cycler
**What goes wrong:** If the cycler mutates `AppContainer.themeResolver` directly, `seedTheme`'s `collect{}` re-applies the persisted tuple on the next profile/theme emission and the cycled style snaps back mid-sweep.
**Why it happens:** There is exactly one resolver and a live collector continuously driving it from persistence (`AppContainer.kt:320-345`).
**How to avoid:** Override LAYER, not resolver mutation. The persisted resolver is never written by the cycler.
**Warning signs:** Theme "flickers back" after a beat; behaves differently while connected (active profile) vs idle.

### Pitfall 2: Views surfaces don't flip with the override
**What goes wrong:** Compose surfaces flip (they read `LocalTokens`) but `GraphView`/`BedMeshHeatmapView`/`WebcamView` stay on the old theme.
**Why it happens:** Views don't read `LocalTokens`; they receive tokens pushed via `applyTokens(t)` from their `*Host`'s `update{}` block, which collects a tokens flow at the call site (`GraphViewHost.kt:36-39`).
**How to avoid:** Make the `*Host` callers (and `DinghyTheme`) collect the SAME `effectiveTokens` (override-aware) flow, not `themeResolver.tokens` directly. Audit every `applyTokens` call site.
**Warning signs:** The temp graph / bed mesh / webcam frame border keeps the persisted theme while the rest of the app cycles.

### Pitfall 3: Back-intent inconsistency is the actual sweep weight (not token purity)
**What goes wrong:** Treating the sweep as a raw-color hunt finds ~4 sanctioned literals and declares victory, while the real LAW divergence — Back rendered as `Danger`/`Go`/`Neutral` on different screens — goes unfixed.
**Why it happens:** CONTEXT's "9 hits / mostly verification" is true for *token purity* but the heavy dimension is *button-intent*, and Back is the worst offender.
**How to avoid:** The AUDIT.md scorecard must score the **button-intent** dimension per screen, and specifically inventory every `onBack` → `Intent` mapping. Confirmed offenders to fix to `Intent.Neutral`: `ExtrudeScreen` (Danger), `TemperatureScreen` (Go), `SpoolScreen` (Danger), `WebcamScreen` (red), `ConsoleScreen`/`Files`/calibration pages (verify each). Already correct: `MoveScreen` (Neutral, the 15.1 reference). [VERIFIED: grep across ui/**]
**Warning signs:** Back is a different color screen-to-screen; the THEMING.md "Back = NEUTRAL, consistent gutter position" rule has visible exceptions.

### Pitfall 4: Back POSITION, not just color
**What goes wrong:** Fixing Back's color but leaving it in a different gutter slot per screen violates the D-10 "consistent gutter location app-wide" rule (right-aligned or centered, never varying).
**How to avoid:** The audit must also score Back POSITION. This is a layout check the cycler can't reveal (color tool) — it's eyeballed in the D-10 guided batch and recorded in AUDIT.md.

### Pitfall 5: fsSp false-negatives in the grep
**What goes wrong:** A grep for `fontSize = <number>.sp` flags `SpoolScreen` (8 hits, "0 via fsSp") as a violator.
**Why it happens:** SpoolScreen computes `val headerSp = fsSp(26f, t.fs)` then uses `fontSize = headerSp.sp` — correct, but the literal `fsSp` isn't on the `fontSize` line.
**How to avoid:** When auditing fsSp, trace local `val …Sp = fsSp(...)` definitions, don't pattern-match the `fontSize=` line alone. [VERIFIED: SpoolScreen.kt:257-259 — all via fsSp]

## Code Examples

### Override-aware effective-tokens flow (the core mechanism)
```kotlin
// di/AppContainer.kt — NEW
/** Transient cycler override (D-06–D-08). null = use the real persisted theme. NOT persisted. */
private val _themeOverride = MutableStateFlow<ThemeOverride?>(null)
val themeOverride: StateFlow<ThemeOverride?> = _themeOverride.asStateFlow()
fun setThemeOverride(o: ThemeOverride?) { _themeOverride.value = o }   // dismiss → setThemeOverride(null)

// A SECONDARY resolver used ONLY to bake override tuples — never fed by seedTheme, never persisted.
private val overrideResolver = ThemeResolver()

/** Override-aware tokens both toolkits consume. Source: themeResolver.compute() path reused. */
val effectiveTokens: Flow<ThemeTokens> =
    combine(themeResolver.tokens, _themeOverride, activeProfile) { persisted, ov, profile ->
        if (ov == null) persisted
        else {
            // Keep the user's real seed/pool; override only dark/mode (+ fs for the size cycler).
            val base = profile?.toThemeTuple() ?: persisted.let { /* idle tuple */ }
            overrideResolver.apply(
                seedHex = base.seedHex, dark = ov.dark ?: base.dark,
                paletteMode = ov.paletteMode ?: base.paletteMode,
                poolShift = base.poolShift, maxItems = base.maxItems,
                overrides = base.poolOverrides.mapValues { it.value.toComposeColor() },
                fs = ov.fs ?: base.fs,
            )
            overrideResolver.tokens.value
        }
    }
// DinghyTheme(resolver=…) becomes DinghyTheme(tokensFlow = container.effectiveTokens);
// every *Host call site collects container.effectiveTokens instead of themeResolver.tokens.
```
*(Shape illustrative — the planner refines exact tuple plumbing; the load-bearing facts are: one override StateFlow, a secondary resolver for baking, both consumers switch to `effectiveTokens`.)* [Source: synthesized from theme/ThemeResolver.kt + di/AppContainer.kt:320-345, read this session]
