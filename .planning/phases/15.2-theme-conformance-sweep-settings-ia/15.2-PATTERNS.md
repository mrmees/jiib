## The three load-bearing facts the planner must internalize

These three were verified by reading the actual code this session; they shrink the phase materially.

### FACT 1 — There is ONE token root, and it is `LocalTokens` (the override slots in front of it ONCE)
`MainActivity.kt:42` is the single `DinghyTheme(container.themeResolver)` boundary for the whole app.
`DinghyTheme` (`theme/compose/DinghyTheme.kt:39`) collects `resolver.tokens` and provides it to
`LocalTokens` (`theme/compose/LocalTokens.kt:20`, a `staticCompositionLocalOf`). **Every Compose
surface reads `LocalTokens.current`.** The override layer's whole job is to make `DinghyTheme`
collect an *override-aware* flow instead of `resolver.tokens` directly — a one-line swap at
`MainActivity.kt:42` + a new derived flow on `AppContainer`. No per-screen change.

### FACT 2 — The classic-Views surfaces ALSO flip for free, because their hosts read `LocalTokens.current`
RESEARCH's Pitfall 2 ("Views won't flip with the override") is **already mitigated by the existing
call-site shape** and the planner should NOT build a second Views token path. Proof:
- `GraphViewHost(tokens = …)` / `BedMeshHeatmapHost(tokens = …)` / `WebcamViewHost(tokens = …)` take
  `tokens` as a **parameter** (`render/GraphViewHost.kt:29`, `render/BedMeshHeatmapHost.kt:30`,
  `render/WebcamViewHost.kt:38`) and push it via `view.applyTokens(tokens)` (`GraphViewHost.kt:37`).
- The CALLERS pass `tokens = LocalTokens.current`: `TemperatureScreen.kt:114` (`val t = LocalTokens.current`)
  → `:159` (`tokens = t`); `AppShell.kt:126` (`val t = LocalTokens.current`) → `:530/:540/:549/:556`
  (`tokens = t` into the BedMesh/calibration screens).
- Therefore the Views hosts already root in `LocalTokens`. Flip `LocalTokens` (FACT 1) and
  `applyTokens` fires with the override tokens on the next recomposition. **No `effectiveTokens` plumbing
  into the `*Host`s is needed** — only the single `DinghyTheme` collect changes.

> ⚠ The one thing to verify at build: that NO Views host call-site collects `themeResolver.tokens`
> directly (bypassing `LocalTokens`). The grep this session found none — every host gets `LocalTokens.current`.

The 15.1-D-10 LAW makes Back **`Intent.Neutral`** app-wide (reference: `MoveScreen.kt:228` — the canonical
"Back = Neutral" with the D-10 doc-comment). Confirmed offenders to flip:

## Pattern Assignments

### `theme/ThemeOverride.kt` + `di/AppContainer.effectiveTokens` (model + derivation, transform)

**Analogs:** `theme/ThemePrefs.kt:127-139` (the `ThemeTuple` model), `di/AppContainer.kt:320-345`
(the `seedTheme` collect/`apply` path the override re-uses), `di/AppContainer.kt:192-200` (the
`MutableStateFlow` + `asStateFlow()` publish shape).

**Override-StateFlow shape** — copy the `_spine`/publish idiom (`AppContainer.kt:192-200`):
```kotlin
// di/AppContainer.kt — NEW (mirrors _spine / spine at :192-200)
private val _themeOverride = MutableStateFlow<ThemeOverride?>(null)
val themeOverride: StateFlow<ThemeOverride?> = _themeOverride.asStateFlow()
fun setThemeOverride(o: ThemeOverride?) { _themeOverride.value = o }   // dismiss → setThemeOverride(null)
```

**Override token GENERATION** — do NOT mutate `themeResolver` (FACT below). Bake via a SECONDARY,
never-seeded `ThemeResolver` reusing its `apply()` (`ThemeResolver.kt:114-133`) + the fail-safe
`compute()` try/catch (`ThemeResolver.kt:152-170`):
```kotlin
private val overrideResolver = ThemeResolver()   // never fed by seedTheme; never persisted

val effectiveTokens: Flow<ThemeTokens> =
    combine(themeResolver.tokens, _themeOverride, activeProfile) { persisted, ov, profile ->
        if (ov == null) persisted
        else {
            val base = profile?.toThemeTuple() ?: themePrefs /* idle tuple */
            overrideResolver.apply(            // reuses ThemeResolver.apply ONE-recompute path (:114)
                seedHex = base.seedHex,                       // user's REAL seed (D-06)
                dark = ov.dark ?: base.dark,                  // style cycler overrides dark
                paletteMode = ov.paletteMode ?: base.paletteMode, // style cycler overrides mode
                poolShift = base.poolShift, maxItems = base.maxItems,
                overrides = base.poolOverrides.mapValues { it.value.toComposeColor() },
                fs = ov.fs ?: base.fs,                        // size cycler overrides fs
            )
            overrideResolver.tokens.value
        }
    }
```

**WHY a second resolver, not `themeResolver.setMode()` (the rejected GalleryScreen mechanic):** the
`seedTheme` collector (`AppContainer.kt:320-345`) continuously re-applies the persisted tuple on every
profile/theme emission; mutating the live resolver would be FOUGHT and snapped back mid-sweep (RESEARCH
Pitfall 1). The override layer never touches the persisted resolver — dismiss = `setThemeOverride(null)`,
deterministic snap-back.

**`ThemeOverride` model** — a sparse nullable tuple (only the cycled axes), copy the `ThemeTuple`
data-class shape (`ThemePrefs.kt:127-139`):
```kotlin
// theme/ThemeOverride.kt — NEW
data class ThemeOverride(
    val dark: Boolean? = null,        // null = fall through to the active profile's persisted value
    val paletteMode: String? = null,  // style cycler steps {Colorful, Simple, HighContrast}
    val fs: Float? = null,            // size cycler steps S/M/L (FontScale.*.multiplier)
)
```

**DinghyTheme wiring** — swap the collected flow (`DinghyTheme.kt:39`):
```kotlin
// BEFORE: val tokens by resolver.tokens.collectAsStateWithLifecycle()
// AFTER : pass container.effectiveTokens in; collect THAT. Keep the LocalDensity fontScale=1f line (:43) UNCHANGED.
```
`MainActivity.kt:42` changes from `DinghyTheme(container.themeResolver)` to passing the override-aware
flow (planner picks the exact signature — either `DinghyTheme(tokensFlow = container.effectiveTokens)`
or keep the resolver param + add an override param).

### `ui/shell/DevThemeCyclerOverlay.kt` (overlay widget, event-driven)

**Analog:** the AppShell overlay grammar — `MacroExecutionPopup` / `ScanSurface` / `PromptDialog` are
rendered as Boxes INSIDE `AppShell`'s `BoxWithConstraints`, AFTER `when(dest)`, gated on a flag
(`AppShell.kt:608-639` for ScanSurface; `:647-694` for PromptDialog). Drag from `designsystem/ScrubberPage.kt`.

**Overlay placement pattern** (copy the gated-Box-after-when(dest) shape, `AppShell.kt:626-639`):
```kotlin
// inside AppShell BoxWithConstraints, after the existing overlays, gated on the dev-enable boolean:
if (devCyclerEnabled) {
    DevThemeCyclerOverlay(
        onCycleStyle = { container.setThemeOverride(nextStyleOverride) },  // tap → advance the 6 combos
        onCycleSize  = { container.setThemeOverride(nextSizeOverride) },   // separate widget (D-07)
        onDismiss    = { container.setThemeOverride(null) },               // restore real theme
    )
}
```

**Adreno-320 motion law (D-13 / CLAUDE.md):** static only — NO continuous/looping animation on the
widget (the same rule `OutlinedControl.kt:62-66` documents: "NO looping/infinite Compose transition").
A one-shot tap ripple is fine; a pulsing glow is not. Every color via `LocalTokens` (it themes WITH the app).

**Draggable position (Claude's discretion):** `Modifier.offset{} + detectDragGestures` — precedent in
`designsystem/ScrubberPage.kt`. Or fixed corner via `Modifier.align(Alignment.*)` (the
`AppShell.kt:697-703` bottom-edge handle shape).

**Anti-pattern (RESEARCH):** do NOT use a `WindowManager` `TYPE_APPLICATION_OVERLAY` (needs
`SYSTEM_ALERT_WINDOW` permission). The in-AppShell Box is the established grammar and flips with the
same tokens.

## Shared Patterns

### Token purity (the audit standard — mostly verification)
**Source:** `theme/compose/LocalTokens.kt:20` + `theme/ThemeTokens.kt`. Every chrome color reads
`LocalTokens.current.<role>`; the audit confirms zero raw `Color(0x…)`. RESEARCH found only **4
sanctioned literals in 3 files** — all DATA, explicitly carved out by THEMING.md: `PromptMarkupText.kt`
(author-hex carve-out), `SpoolPicker.kt` (filament swatches), `SettingsScreen.kt`/`ThemeEditorScreen.kt`
(theme swatches). **Do NOT "fix" these** (RESEARCH Anti-Pattern). Treat as conformant in AUDIT.md.

### fsSp font-size discipline
**Source:** `theme/fsSp` + `DinghyTheme.kt:43` (the `fontScale=1f` density override making `--fs` sole
authority). Reference uses: `OutlinedControl.kt:109/115/124` (`fsSp(22f|18f, t.fs)`), `AppDrawer.kt:242/249/260`.
**Audit trap (RESEARCH Pitfall 5):** trace `val …Sp = fsSp(…)` definitions, don't grep the `fontSize=`
line alone (e.g. `SpoolScreen.kt:257-259` defines `val headerSp = fsSp(26f, t.fs)` then uses it). Floors
per `[[dinghy-font-sizes-too-small]]`: 15sp metadata, 17–18 body, 20–22 titles, 26 stats, 30+ focus.

### Button-intent color (the heavy audit dimension)
**Source:** `designsystem/control/OutlinedControl.kt:39-54` (the `Intent` enum + `outlineColor` map).
**Apply to:** every gutter/action button — score the `onBack → Intent` mapping per screen (FACT 3) and
the red/green/amber/accent intent correctness per CLAUDE.md grammar.

### Durable persistence (write-scope-cancellation lesson)
**Source:** `AppContainer.kt:107` (`writeScope`) + `:130-132` (`mutateActiveProfile`) +
`ProfileStore.kt:109-118` (`mutateActive`) + `ThemePrefs.kt:94-99` (`mutateOverrides`).
**Apply to:** every persisted write this phase — the D-04 per-profile toggles, the absorbed Connection
save, the dev-enable boolean. NEVER `rememberCoroutineScope().launch { store… }`
(`[[dinghy-compose-write-scope-cancellation]]`, documented at `AppContainer.kt:97-105`). The cycler
override is the EXCEPTION — it persists NOTHING (only `setThemeOverride`, an in-memory StateFlow).

### Overlay grammar (above all routes)
**Source:** `AppShell.kt:608-694` (MacroExecutionPopup / ScanSurface / PromptDialog gated Boxes after
`when(dest)`). **Apply to:** the DevThemeCyclerOverlay.
