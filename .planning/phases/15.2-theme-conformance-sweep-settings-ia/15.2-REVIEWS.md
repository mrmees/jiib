# Cross-AI Plan Review — Phase 15.2

## Codex Review

**Summary**

The plan set is directionally sound and unusually strong on sequencing, local tests, and on-device gates, but I would not treat it as ready without revisions. The highest risks are in the override-layer details and audit closure mechanics: the current `effectiveTokens` shape is under-specified for idle/global theme fallback and can race/mis-restore; the cycler steppers can accidentally clear each other's axis; disabling the dev widget can leave an override stuck; and the final sweep lacks a hard closed loop for on-device-discovered gaps.

**Strengths**

- Cyclers-first sequencing is correct for this phase; it materially reduces sweep cost.
- The plans preserve the known persistence lesson by routing durable writes through `AppContainer.writeScope`.
- Wave-0 compile-clean RED scaffolds directly address the prior Gradle `--tests` trap.
- The Settings IA split mostly matches the project decisions: Printers for connection, Theme for look, Settings for feature toggles, About for app-global metadata.
- Human on-device gates are appropriate here; visual conformance cannot be fully proven by host unit tests.
- Sanctioned raw-color carve-outs are explicitly named, which reduces overzealous "fixing."

**Concerns**

- **HIGH:** `effectiveTokens = combine(themeResolver.tokens, override, activeProfile)` is not enough to faithfully bake overrides. When `activeProfile == null`, the plan says to use the idle `ThemePrefs` tuple, but that tuple is not in the combine inputs. Also, `themeResolver.tokens` and `activeProfile` can briefly represent different profiles because `seedTheme()` applies after profile emission.
- **HIGH:** The secondary `overrideResolver` is shared mutable state inside a Flow transform. If there are multiple collectors, one collector can call `apply()` and another can overwrite the resolver before the first reads `tokens.value`. Make baking pure or return the snapshot under the same lock.
- **HIGH:** The override tuple risks dropping persisted theme fields. The plan mentions seed/pool fields but does not clearly require carrying `statusOverrides`. Any future resolver input would be easy to forget, causing the cycler theme to diverge from real theme semantics.
- **HIGH:** The cycler steppers as described can clear each other. `nextStyleOverride()` leaving `fs = null` and `nextSizeOverride()` leaving `dark/paletteMode = null` means tapping Size after Style may restore persisted style, not preserve the active style override.
- **HIGH:** Disabling the dev widget can hide the overlay without clearing `_themeOverride`. If About toggles dev widgets off while an override is active, the app may remain visually overridden with no visible dismiss control.
- **HIGH:** The final audit loop is not closed. Wave 06 fixes executor-identified mechanical findings, then asks the owner to verify. If the owner finds new mechanical gaps on-device, Task 4 only talks about judgment-call decisions, not looping back through fix → build → reinstall → verify.
- **MEDIUM:** Plan 06 may miss core-screen findings discovered in Wave 05. Wave 05 says guided-review mechanical issues are recorded for Wave 06, but Wave 06 Task 2 is framed around long-tail findings from Task 1.
- **MEDIUM:** The AUDIT coverage proof is too weak. `grep -c` checks and a hand-built row list will miss overlays, dialogs, adapters, drawer chrome, splash/connect prompts, scan surfaces, prompt image/content components, and other non-screen surfaces.
- **MEDIUM:** The Plan 02 release checkpoint has no clean way to enable the widgets before About exists. "Temporarily flip the persisted boolean" needs an exact, repeatable method or the blocking checkpoint is fragile.
- **MEDIUM:** The `webcamEnabled` feature toggle is tested for persistence but not clearly wired to behavior. A Settings functionality toggle that does not gate the Webcam tile, screen, or stream/probe behavior will pass tests while failing user intent.
- **MEDIUM:** Connection move needs sharper API-key behavior. "Never surface raw key" is not enough; define whether the existing key is preserved when the field is blank, how to clear it, and whether replacement is masked.
- **LOW:** Keeping `Dest.Devices` while user-facing label is "Printers" is acceptable, but copying `DevicesScreen` into `PrintersScreen` risks dead duplicate code and future conformance drift.

**Suggestions**

- Replace the effective-theme base with a single canonical `activeThemeTuple` flow shared by `seedTheme()` and `effectiveTokens`; include idle `ThemePrefs.tupleFlow`.
- Add a pure `ThemeResolver.resolve(tuple)` / `ThemeResolver.bake(tuple)` API, or an `applyAndSnapshot()` synchronized method, instead of mutating a shared resolver inside a cold Flow.
- Add tests for profile switch while override is active, idle/no-profile override, status override preservation, and disable-dev-clears-override.
- Make cycler steppers preserve non-cycled axes: style updates `dark/paletteMode` while keeping `fs`; size updates `fs` while keeping style.
- When `devCyclerEnabled` becomes false, clear `_themeOverride`, or make `effectiveTokens` ignore overrides while disabled.
- Add an explicit audit inventory script/check: generated surface list from `ui/**` and `render/**`, expected AUDIT rows, no open cells, whitelist-only raw colors, no `MaterialTheme.colorScheme`, no raw `.sp` outside approved helpers.
- Amend Wave 06 to loop until owner on-device verification reports no remaining mechanical gaps.
- Define D-13 more tightly: mechanical = direct token/intent/font/target violation; judgment = changes hierarchy, density, workflow, information priority, or deliberate data visualization.

**Risk Assessment**

Overall risk: **HIGH**. The plans are strong enough to execute after revision, but the phase touches global theming, navigation IA, persistence, and every surface. The main risk is not test failure; it is green host tests plus a visually or behaviorally wrong device build. The on-device gates are well placed, but they need a stricter closure loop and the override architecture needs hardening before the sweep depends on it.

## Consensus Summary

Only one external reviewer (Codex) was available this run (`claude` skipped for independence; no other CLIs installed), so there is no cross-model consensus to triangulate. Codex's verdict is **revise-before-execute (HIGH risk)** — not because the plans are wrong-headed (sequencing, tests, and on-device gates are praised) but because the **override-layer architecture in plan 01** and the **audit-closure mechanics in plans 05/06** have concrete, fixable gaps that the rest of the phase depends on.

### Agreed Strengths
- Cyclers-first sequencing (D-09) is the right call and genuinely reduces sweep cost.
- writeScope persistence discipline + Wave-0 compile-clean RED scaffolds correctly honor prior project lessons.
- On-device human gates are appropriately placed for inherently-visual conformance work.
- Sanctioned-literal carve-outs are explicit, preventing overzealous "fixing."

### Highest-Priority Concerns (Codex HIGH — address before execute)
1. **Override baking is under-specified and racy (plan 01).** Three distinct HIGHs cluster here:
   - `effectiveTokens` combine omits the idle/no-profile `ThemePrefs` tuple, and `themeResolver.tokens` vs `activeProfile` can transiently disagree (seedTheme applies *after* profile emission).
   - The shared mutable `overrideResolver.apply(...)` → read `tokens.value` inside a cold Flow transform is not safe under multiple collectors. Prefer a **pure `bake(tuple)`/`resolve(tuple)`** or a synchronized `applyAndSnapshot()`.
   - The override tuple must carry **ALL** resolver inputs (notably `statusOverrides`/pool fields), or the cycled theme silently diverges from real theme semantics.
2. **Cycler steppers can clear each other's axis (plan 02).** Style-advance leaving `fs=null` and size-advance leaving `dark/paletteMode=null` means the second tap reverts the first axis. Steppers must **merge onto the current override**, preserving non-cycled axes. (The plan's own test `size_cycler_steps...independently` would pass on pure functions yet still ship this bug if the widget passes `null`-filled tuples — worth an explicit "preserve active style override" test.)
3. **Disabling dev widgets can strand an active override (plans 02/04).** Turning the About toggle off hides the overlay (and its dismiss affordance) without clearing `_themeOverride`. Either clear the override when `devCyclerEnabled→false`, or make `effectiveTokens` ignore overrides while disabled.
4. **Audit loop isn't closed (plan 06).** Task 4 only resolves judgment-calls; there's no fix→build→reinstall→re-verify loop for **new mechanical gaps the owner finds on-device**. Add an explicit "loop until owner reports no remaining mechanical gaps" closure.

### Worth Folding In (Codex MEDIUM)
- **Wave-05 core-screen mechanical findings** must explicitly flow into Wave-06 Task 2 (currently framed only around long-tail/Task-1 findings) — a coverage seam.
- **AUDIT coverage proof is too weak** (`grep -c` + hand-built rows): generate the surface inventory from `ui/**`+`render/**` so overlays/dialogs/drawer-chrome/scan-surface/prompt components aren't silently missed. Pair with a lint-style check (whitelist-only raw colors, no `MaterialTheme.colorScheme`, no raw `.sp` outside `fsSp`).
- **Plan-02 pre-About enablement** needs an exact, repeatable method to flip the dev boolean before the About toggle exists (the blocking checkpoint is otherwise fragile).
- **`webcamEnabled` must gate real behavior**, not just persist — otherwise a green test masks a dead toggle (a textbook mock-vs-reality trap for this project).
- **Connection-move API-key semantics**: define blank-field-preserves-existing vs clear vs masked-replace, not just "never surface raw."
- **Tighten D-13**: mechanical = direct token/intent/font/target violation; judgment = anything touching hierarchy/density/workflow/information-priority/deliberate data-viz.

None — single reviewer.
