<decisions>
## Implementation Decisions

### Settings information architecture (the deferred boundary)
The old monolithic Settings page is **dissolved** into separate App-Drawer destinations. This
kills the Connection-redundant-with-Devices problem the owner flagged in Phase-15 UAT.

- **D-01: Four drawer destinations** — **Printers · Theme · Settings · About**. Each is its own
  App-Drawer tile. There is no longer a single "Settings" page that owns everything.
- **D-02: Printers (= today's Devices screen, renamed)** owns printer **add / remove / switch**
  AND **connection (host/port/key)** — Connection moves OUT of Settings into here. Room reserved
  for printer-specific connection extras down the line. (Existing `DevicesScreen.kt` is the base;
  rename user-facing label Devices → **Printers**.)
- **D-03: Theme tile** — its own drawer destination; controls the *look* (theme/accent/text-size,
  the existing ThemeEditor content promoted out of Settings). **Per-printer** — changes with the
  active printer (keeps Phase-14 per-profile theming; "tell my printers apart by color").
- **D-04: Settings tile** — its own drawer destination; controls *functionality* (feature
  toggles). **Truly per-printer / per-profile** — each profile stores its own toggles (e.g. webcam
  on the printer that has a camera, off on the other; matches Phase-14 webcam-pref re-keying by
  profileId). NOT one app-wide set shown here.
- **D-05: About tile** — its own (4th) small drawer destination for the genuinely **app-global**
  items (version, about, app-wide/system info, and the hidden dev-widget enable from D-08). Keeps
  Printers/Theme/Settings purely per-printer with clean page identity.

### Dev theme-cycler widgets (owner's idea — conformance accelerant)
Two independent floating widgets that make eyeballing every screen across every theme combo fast.

- **D-06: Style cycler** — a floating widget; **tap = advance through the 6 main styles** =
  `{dark, light} × {Colorful, Simple, High-Contrast}`. Uses the user's **current accent/seed**
  (tests the real themes, not a demo palette). Does NOT step text-size (that's D-07).
- **D-07: Text-size cycler** — a **separate** floating widget that toggles **S / M / L** (`--fs`).
  Independent of D-06 so each axis can be swept on its own.
- **D-08: Apply live, app-wide + release-available behind a hidden toggle.** A tap APPLIES the
  combo to the **whole live app** (real theme flips globally; navigate anywhere and every screen
  renders in it) — this is what makes it a true walk-the-app sweep tool, not a single-screen
  preview. Available in **release** builds (the owner sideloads release APKs onto flox), gated
  behind a **hidden enable** (a dev toggle living in the **About** tile, D-05). On dismiss/disable
  it **restores the user's real saved theme** (the cycler must not clobber the persisted
  per-profile theme tuple).
- **D-09: These widgets are a phase-early deliverable** — build them first so both the guided
  review (D-10) and the app-wide audit (D-11) ride on them.

### Conformance sweep — coverage, method, conflict policy
- **D-10: Staged sweep — guided FIRST batch, then turn it loose.** Do the first **~5–10 daily-
  driver core screens** as an **interactive on-device screen-by-screen review** with the owner
  (the established edit→build→install→owner-eyeballs loop, `[[dinghy-display-ondevice-iteration]]`).
  **Purpose: surface any latent design/UI criteria not yet captured in the LAW** before an
  app-wide audit runs. Findings from this batch **fold back into `docs/ui_design/THEMING.md` + the
  audit checklist** so the hardened criteria propagate to the rest of the sweep and to future
  phases. Suggested first batch (confirm at plan time): Home/Print-Status, Move, Temperature,
  Files, Print controls, Console, Settings/Theme/Printers (the new IA surfaces).
- **D-11: Coverage = ALL ~30 surfaces, heavy, this phase.** Core + the long tail (calibration,
  spool, webcam, macros, prompt). The cycler widgets make per-screen checks cheap enough that
  the long tail isn't deferred. (Matches roadmap "heavy sweep of everything that exists today.")
  The light re-sweep of LATE surfaces 16–20 still folds into Ship.
- **D-12: Audit method = tracked AUDIT.md scorecard then fix** — score each surface × the 6 LAW
  dimensions in an AUDIT.md so coverage is visible and nothing slips; then fix findings. (The D-10
  guided batch hardens the dimension list before the scorecard is applied app-wide.)
- **D-13: Conflict policy = fix mechanical violations silently, flag judgment calls.** Clear-cut
  violations (raw color, wrong button-intent, sub-64px target, sub-`fsSp` font, broken
  light/custom rendering) get fixed without stopping. Pause and ask the owner ONLY on genuine
  design-judgment conflicts where the new LAW vs a deliberate existing choice actually collide.

### Claude's Discretion
- Exact widget rendering: draggable bubble vs fixed corner, the on-widget label/affordance showing
  the current combo, long-press-to-hide vs a toggle in About — planner/owner's call within D-06–D-08.
  (The widgets are FFG-exempt dev chrome, not user-facing product UI.)
- The mechanism for applying a transient global theme without persisting it (so dismiss restores the
  real per-profile tuple) — must NOT route through the persist path; honor
  `[[dinghy-compose-write-scope-cancellation]]` if any state is written.
- Exact AUDIT.md scorecard format/columns and the final ordering of the long-tail sweep.
- Exact re-layout of the four IA destinations within Focus/Field/Gutter (Settings/Theme are
  FFG-exempt keyboard-allowed surfaces per UI LAW; Printers inherits the Devices layout).
- Whether the dev-widget hidden enable is a tap-count easter egg vs a plain About toggle.

  Connection → Printers; Theme + Settings split per-printer; About for app-global). The owner chose

<code_context>
## Existing Code Insights

### Reusable Assets
- **Token discipline is already largely healthy** — a quick scan found only 9 raw-color hits
  across 4 files (`PromptMarkupText.kt` = the Phase-12 D-03 author-hex carve-out; `SpoolPicker.kt`
  = actual filament colors = data, not chrome; `ThemeEditorScreen.kt`/`SettingsScreen.kt` = theme
  swatches). The token-purity dimension is mostly verification, not mass refactor. The sweep's real
  weight is button-intent, FFG grammar, ≥64px, and **fsSp font sizing**.
- **`DevicesScreen.kt` (Phase 14)** is the base for the Printers tile — it already owns
  add/delete/switch; the sweep folds Connection editing into it.
- **`ThemeEditorScreen.kt` + the Settings hub (Phase 15)** are promoted/split, not rebuilt — Theme
  content moves to its own tile, toggles to the Settings tile.
- **The App-Drawer (`AppDrawer.kt`) already hosts a live Devices tile (Phase 14)** — extend its
  tile set to the four D-01 destinations.
- **`ThemeResolver` generate-and-cache + the per-profile theme tuple** are the integration point for
  the cycler's transient global apply.

### Established Patterns
- **Settings/Theme are FFG-exempt, keyboard-allowed surfaces** (UI LAW) — the FFG-grammar audit
  dimension does NOT apply to them the way it does to printer-control screens.
- **Per-profile persistence via `AppContainer.writeScope` + `mutateActive{}`** — D-04's per-printer
  toggles join the existing per-profile tuple the same way.
- **Token-routed chrome only** — the audit's token-purity dimension is enforcing an existing rule,
  not introducing one.

### Integration Points
- The cycler widgets must overlay the whole app (above all routes) and apply a theme combo without
  persisting — a transient resolver override distinct from the persisted per-profile theme.
- The four IA destinations all route through the App-Drawer / ShellNavState; the rename
  Devices→Printers touches drawer label + any nav refs.
