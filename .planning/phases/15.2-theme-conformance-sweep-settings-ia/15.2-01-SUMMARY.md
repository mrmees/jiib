# Phase 15.2 Plan 01: Transient Theme-Override Layer + Dev-Enable + AUDIT Scaffold Summary

Built the phase-early foundation (D-09) for the conformance sweep: a transient, never-persisting theme
override that re-themes the WHOLE live app (Compose + classic-Views) from a single canonical tuple via a
PURE `effectiveTokens` flow, plus the app-global release-readable dev-enable boolean, the pure
`ThemeResolver.bake(tuple)`, and the surface-granular `15.2-AUDIT.md` scorecard.

## What was built

- **`ThemeResolver.bake(tuple)` (HIGH-2)** — `compute()` was refactored into a pure `computeFrom(...)`
  taking explicit inputs; `compute()` delegates to it (live path byte-identical) and `bake(tuple)` maps
  the tuple's wire-form overrides via `toComposeColor()` and calls `computeFrom`. `bake` reads no `var`
  field, never assigns `_tokens`, needs no `synchronized` — concurrent collectors cannot tear.
- **`ThemeOverride` + `mergeOnto` (HIGH-3)** — sparse nullable `(dark, paletteMode, fs)`; `mergeOnto`
  uses `base.copy(...)` so every other tuple field (seedHex, poolShift, maxItems, poolOverrides,
  **statusOverrides**) passes through verbatim.
- **`AppContainer.activeThemeTuple` (HIGH-1)** — the inline `if (p != null) flowOf(p.toThemeTuple()) else
  themePrefs.tupleFlow` was hoisted out of `seedTheme()` into ONE canonical flow that BOTH `seedTheme`
  (applies it) and `effectiveTokens` (bakes it) derive from — no profile skew, no idle omission.
- **`AppContainer.effectiveTokens` (HIGH-1)** — `combine(activeThemeTuple, _themeOverride,
  devCyclerEnabled)` baking PURELY in both branches via `themeResolver.bake`; never reads
  `themeResolver.tokens` (so the non-override path can't emit a snapshot lagged behind `seedTheme`'s async
  apply). Override baked only while dev enabled (`!devOn` gate = HIGH-5).
- **`setThemeOverride` / `updateThemeOverride` (atomic, MEDIUM)** — both in-memory only (no DataStore
  write); `updateThemeOverride` via `_themeOverride.update{}` so rapid taps can't lose an axis.
- **Dev-enable boolean (D-08)** — `ThemePrefs.devEnableFlow` (default false, release-readable, NOT
  `BuildConfig.DEBUG`) + `setDevEnable`; `AppContainer.devCyclerEnabled` + `setDevCyclerEnabled` which on
  OFF clears the override (HIGH-5 belt-and-suspenders) and persists via the process-lifetime `writeScope`.
  Carries the `// TEMP(15.2-02)` note: plan 02 flips the default true for its pre-About release walk, plan
  04 reverts to false (canonical end-state).
- **`DinghyTheme(tokensFlow)` overload** — collects the override-aware flow; the resolver overload is
  retained for BenchActivity + instrumented tests. `MainActivity` now passes `container.effectiveTokens`.
- **`15.2-AUDIT.md`** — D-12 scorecard generated from a programmatic `ui/**`+`render/**` inventory (command
  recorded), multi-surface files (AppShell overlays, prompt dialog vs markup vs image) EXPANDED into 32
  distinct surface rows; 6+1 LAW dimension columns; D-13 conflict policy + sanctioned-literals note.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] `ThemeOverride.kt` created in Task 4 instead of Task 3**
- **Found during:** Task 4
- **Issue:** Task 4's forward-declared `_themeOverride` field/`setThemeOverride` reference the
  `ThemeOverride` type, which the plan slated for creation in Task 3 — Task 4 could not compile standalone
  without it.
- **Fix:** Created the full `ThemeOverride.kt` (data class + `mergeOnto`) during Task 4 (it has no
  Task-3-specific dependency). Task 3 then consumed it rather than re-creating it. The `build_order`
  explicitly sanctioned a forward-declaration here; creating the whole tiny file is the cleanest form.
- **Files modified:** app/src/main/java/works/mees/dinghy/theme/ThemeOverride.kt
- **Commit:** ff80d3e

**2. [Rule 3 - Blocking] Retained a resolver-based `DinghyTheme` overload**
- **Found during:** Task 3
- **Issue:** Changing `DinghyTheme(resolver)` → `DinghyTheme(tokensFlow)` broke `BenchActivity` (main) +
  four androidTest call sites (`ScanSurfaceLifecycleTest`, `ShellPresenceTest`, `DrawerWebcamGatingTest`,
  `WebcamUnsupportedCardTest`, `WebcamLifecycleTest`) that drive a bare `ThemeResolver`.
- **Fix:** Added a `DinghyTheme(resolver)` overload that delegates to the Flow overload via
  `resolver.tokens`. Production host (MainActivity) uses the Flow + `effectiveTokens`; bench/instrumented
  keep the resolver path. Both share the `--fs` density authority.
- **Files modified:** app/src/main/java/works/mees/dinghy/theme/compose/DinghyTheme.kt
- **Commit:** 7454fe3
