## Architecture Patterns

### R5a: Lint Baseline Under JDK-17 Toolchain

The AGP 8.7 / JDK-21 UAST crash is a known issue: the lintVital UAST detectors bundled with AGP 8.7 crash with `IncompatibleClassChangeError` under JDK 21. The fix is to run lint under JDK 17. `[ASSUMED]` (training knowledge; Gemini query timed out)

In AGP 8.7, `kotlin { jvmToolchain(17) }` sets the JVM for BOTH Kotlin compilation AND the Gradle daemon that runs lint — the lint process shares the daemon JVM. Therefore, adding `kotlin { jvmToolchain(17) }` to `app/build.gradle.kts` forces lint to run under JDK 17. The dev box remains JDK 21 (used for Gradle bootstrapping), but `org.gradle.java.home` or the toolchain resolution downloads JDK 17 automatically via the Gradle Toolchain API. `[ASSUMED]`

**Lint baseline generation:** `[ASSUMED]`
```bash
/mnt/c/Windows/System32/cmd.exe /c "E:\Android\gw.bat :app:updateLintBaseline"
```
Then commit `app/lint-baseline.xml`. The `lint {}` block change:
```kotlin
lint {
    baseline = file("lint-baseline.xml")   // use existing baseline
    checkReleaseBuilds = true              // flip to true (was false)
    abortOnError = true                    // flip to true (was false)
    // lintConfig = file("lint.xml")       // optional suppression file if needed
}

kotlin {
    jvmToolchain(17)                       // forces lint to run under JDK 17, resolves UAST crash
}
```
**House rule:** baseline may only shrink, never grow. A new violation added after baseline is committed fails CI.

**NOTE:** `compileOptions { sourceCompatibility = JavaVersion.VERSION_17 }` is already present (line 96-97 of build.gradle.kts) — `jvmToolchain(17)` supplements it by also directing the daemon JVM. These are compatible; `jvmToolchain` is additive here. `[ASSUMED]`

### R10: True Disablement — AdjusterPanel

**Current state (verified at HEAD):** AdjusterPanel L104-107 sets `controlsEnabled = enabled && value != null` and applies alpha+semantics disabled, but L137/192/200 use `onClick = { if (controlsEnabled) reset()/onDecrement()/onIncrement() }` — the `clickable` modifier is ALWAYS present. The tap ripples and swallows the event inside the guard.

**Fix pattern:**
```kotlin
// Pass enabled to clickable modifier directly:
onClick = if (controlsEnabled) reset else null  // Compose: clickable(onClick=null) removes the handler
// OR use Modifier.clickable(enabled = controlsEnabled) { action() }
```

The correct Compose idiom is `Modifier.clickable(enabled = controlsEnabled) { action() }` — when `enabled=false`, `clickable` does not install a touch handler and the ripple is suppressed. `[CITED: developer.android.com/reference/kotlin/androidx/compose/foundation/package-summary#clickable]`

### R10: Dispatcher Rejection Feedback

**Current state (verified):** `CommandDispatcher.dispatch()` L110 (`if (key in _inFlight.value) return`) and L115 (`if (prev != null && now - prev < debounceMs) return`) are silent.

**Fix pattern:** Add a `SharedFlow<String>` (or `StateFlow<String?>`) to CommandDispatcher that emits the rejected `key` on each silent drop. Subscribers (the UI controls) render a brief visual signal (dim-flash, or an `indeterminate` tick animation on the value). The semantics and timing of the debounce ARE NOT CHANGED. `[ASSUMED]`

```kotlin
// In CommandDispatcher:
private val _rejectedKey = MutableSharedFlow<String>(extraBufferCapacity = 4)
val rejectedKey: SharedFlow<String> = _rejectedKey.asSharedFlow()

// At each early return:
if (key in _inFlight.value) { _rejectedKey.tryEmit(key); return }
if (prev != null && now - prev < debounceMs) { _rejectedKey.tryEmit(key); return }
```

### R10: Swipe-Up Accumulation

**Current state (verified):** AppShell L550-551 uses `detectVerticalDragGestures { _, dragAmount -> if (dragAmount < -SWIPE_UP_THRESHOLD_PX) drawerOpen = true }`. This is a per-event check — a single event's `dragAmount` must exceed 80f. The audit confirmed this breaks the `FineTuneNavTest` (swipeUp spreads ~800px over ~12 events, no single event exceeds 80f).

**Fix pattern:** Accumulate drag across the gesture:
```kotlin
var accumulated = 0f
pointerInput(navBackStackEntry, promptView.visible) {
    detectVerticalDragGestures(
        onDragStart = { accumulated = 0f },
        onVerticalDrag = { _, dragAmount ->
            accumulated += dragAmount
            if (accumulated < -SWIPE_UP_THRESHOLD_PX) {
                drawerOpen = true
                accumulated = 0f
            }
        }
    )
}
```
This also closes the `shellpresencetest-device-determinism` / `FineTuneNavTest` harness defect. `[ASSUMED]` — standard gesture accumulation pattern.

### R10: Indication Immediacy

**Current state:** `ListRow` uses `Modifier.clickable(onClick = onClick)` at L115 with no explicit `MutableInteractionSource`. Compose delays press indication in scrollable containers by default for tap/scroll disambiguation. On 20-30fps Adreno 320, this reads as "nothing happened."

**Fix pattern:** Pass an explicit `MutableInteractionSource` and use `Indication` with `delay = 0`:
```kotlin
val interactionSource = remember { MutableInteractionSource() }
Modifier.clickable(
    interactionSource = interactionSource,
    indication = LocalIndication.current,  // or ripple(bounded=true)
    onClick = onClick
)
```
For immediate indication in scrollables, the key is providing an explicit `interactionSource` so Compose does not share it with the parent scrollable's disambiguation logic. `[ASSUMED]` — confirmed pattern from Android training data; Gemini query failed.

### R1: POST_NOTIFICATIONS One-Shot Request

**Verified:** `POST_NOTIFICATIONS` is declared in AndroidManifest L31 but no runtime request exists in the codebase. `[VERIFIED: local codebase]`

**Pattern (Gemini-verified):**
- Register `ActivityResultLauncher` in `MainActivity.onCreate()` (not in a `LaunchedEffect` — must be activity initialization time)
- Trigger at first-connect, gated by `Build.VERSION.SDK_INT >= Build.VERSION_CODES.TIRAMISU` (API 33)
- On API < 33: auto-granted, skip the launch
- On denial: degrade gracefully — app continues working, FGS notification silently absent
- No `shouldShowRequestPermissionRationale` check required for this simple one-shot pattern `[CITED: Gemini response above]`

```kotlin
// MainActivity field:
private val notificationPermLauncher = registerForActivityResult(
    ActivityResultContracts.RequestPermission()
) { /* isGranted: Boolean — no-op on denial, FGS works without notif */ }

// Call at connection established:
fun requestNotificationPermissionIfNeeded() {
    if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.TIRAMISU &&
        ContextCompat.checkSelfPermission(this, Manifest.permission.POST_NOTIFICATIONS)
            != PackageManager.PERMISSION_GRANTED) {
        notificationPermLauncher.launch(Manifest.permission.POST_NOTIFICATIONS)
    }
}
```

The right trigger is when `MoonrakerService` starts (i.e., when the user first saves and connects). `AppContainer` exposes a flow the MainActivity can observe; on the first CONNECTED transition, call `requestNotificationPermissionIfNeeded()`.

### R7: NSC RFC-1918 Scoping

**Current state (verified):** `res/xml/network_security_config.xml` has a single `<base-config cleartextTrafficPermitted="true"/>` — app-wide cleartext. D-11 comment already flags this as a deferred scoping risk. `[VERIFIED: local codebase]`

**NSC does NOT support CIDR notation.** You cannot write `<domain includeSubdomains="true">192.168.0.0/16</domain>`. Domain entries are literal hostnames only. `[ASSUMED]` — confirmed by training knowledge; NSC docs describe only hostnames and `<network-security-config>` spec.

**RFC-1918 pattern:** List the three private ranges as hostname prefixes using wildcards — but NSC also does not support wildcards in domain entries. The correct approach for RFC-1918 scoping is:

1. Set `<base-config cleartextTrafficPermitted="false"/>` (block public-IP cleartext)
2. Add explicit `<domain-config>` entries for the three RFC-1918 /8 roots:

```xml
<network-security-config>
    <!-- Block cleartext to public internet (the new default for base-config) -->
    <base-config cleartextTrafficPermitted="false" />

    <!-- RFC-1918 Class A: 10.0.0.0/8 — permit cleartext for LAN use -->
    <!-- NSC has no CIDR; must use individual subnet anchors or domain prefix approach -->
    <!-- The pragmatic solution: permit by domain suffix for known private ranges -->
    <domain-config cleartextTrafficPermitted="true">
        <!-- 10.x.x.x — any subdomain of .10 is an internal class-A address -->
        <!-- NOTE: NSC domain matching is suffix-based; "10" matches *.10 hostnames, NOT 10.x.x.x IPs -->
    </domain-config>
```

**Critical finding:** NSC domain matching treats IPs as hostnames for matching purposes on API 24+. The `<domain>` element matches the HOST portion of the URL. For IP addresses, there is no wildcard or CIDR support — you can only list exact IPs or use the `<domain-config usesCleartextTraffic="true">` with the configured host explicitly. `[ASSUMED]`

**Pragmatic approach for this LAN-only app:**
```xml
<network-security-config>
    <base-config cleartextTrafficPermitted="false" />
    <!-- Permit cleartext for the Moonraker host configured at runtime.
         We cannot express RFC-1918 as a range; the app reads the host from DataStore.
         The connection screen's host field drives this: any host the user configures
         for a LAN Moonraker will be a private IP or local hostname.
         APPROACH: keep base-config=false; add a user-configured-host escape that
         the app handles by checking against isPrivateAddress() in the socket client,
         or expose a "Allow insecure (HTTP/WS)" toggle that controls whether a
         <debug-overrides> or trust-anchors exception is added. -->
    
    <!-- For the overnight run: add common private range prefixes as domain entries -->
    <!-- The .1 suffix matches hosts ending in ".1" — NOT IPs starting with 10. -->
</network-security-config>
```

**DECISION NEEDED:** NSC cannot express "allow cleartext to all RFC-1918 IPs" declaratively. The practical options are:

A. **Keep `base-config cleartextTrafficPermitted="true"`** but document it as deliberate (LAN-only product, no public deployment risk). Lowest code change. `[ASSUMED]`

B. **Add a runtime "Use HTTP/WS (insecure)" toggle** in Settings that controls a `ConnectionConfig.useSecure` field. The NSC stays permissive, but the URL scheme changes based on user choice. OkHttp handles TLS transparently when `wss://` is used. `[ASSUMED]`

C. **List all commonly encountered LAN IPs** in domain-config (impractical — too many). `[ASSUMED]`

**For R7 tonight:** The CONTEXT.md scope is "NSC cleartext scoped to RFC-1918 + configured host" — given the NSC limitation, the planner should implement **option B**: add `useSecure: Boolean` to `ConnectionConfig` (default `false`), propagate `ws://` vs `wss://` and `http://` vs `https://` through `ConnectionConfig.wsUrl`/`httpBase` properties, add a "Use HTTPS/WSS" toggle in Settings' Connection section, and keep `base-config cleartextTrafficPermitted="true"` (or scope it via a best-effort domain list for the configured host). The cert-failure UX is: `OkHttpClient` with the default trust chain will throw `SSLHandshakeException` on an untrusted cert — catch it in `MoonrakerSocketClient` and emit `SocketEvent.Error("TLS certificate not trusted — check Moonraker reverse-proxy setup")`. `[ASSUMED]`

## Common Pitfalls

### Pitfall 1: enableEdgeToEdge() Placement
**What goes wrong:** Calling `enableEdgeToEdge()` AFTER `super.onCreate()` or after `setContent()` may result in the system bars not rendering transparently or the insets not being dispatched correctly.
**Why it happens:** `enableEdgeToEdge()` configures window decor flags before the view hierarchy is attached.
**How to avoid:** Call `enableEdgeToEdge()` as the FIRST statement in `onCreate()`, before `super.onCreate()`.
**Warning signs:** Status bar has a colored background instead of transparent; content doesn't extend behind system bars.

### Pitfall 2: Lint Baseline Expanding (shrink-only rule)
**What goes wrong:** A future code change introduces a new lint warning, the baseline grows, CI accepts it. The house rule is violated silently.
**Why it happens:** If `abortOnError = true` is not set properly, or the baseline is regenerated carelessly.
**How to avoid:** The `lint { baseline = ... }` block with `abortOnError = true` makes any NEW violation (not in the baseline) fail the build. Never re-run `updateLintBaseline` without a code review of what new violations are being suppressed.
**Warning signs:** `lint-baseline.xml` diff shows new `<issue>` entries being ADDED (not removed).

### Pitfall 3: ABI Split versionCode Collision
**What goes wrong:** Two APKs with the same `versionCode` from different ABI splits confuse package managers and Play (if ever used).
**Why it happens:** `splits {}` without a versionCode offset.
**How to avoid:** Apply `versionCodeOverride` in `applicationVariants.all` (see ABI pattern above). v7a = base, arm64 = base+1.
**Warning signs:** `adb install` for both APKs on a device that supports both complains about version conflict.

### Pitfall 4: CommandCatalogDriftTest Triggered By R4 Incorrectly
**What goes wrong:** Plan author assumes R4 changes CommandSpec, runs the drift test, it fails.
**Why it happens:** Misreading the scope — R4 rewires EXISTING specs to read from CommandMap, it does NOT add new specs.
**How to avoid:** Confirm `catalogId` values are unchanged after rewire. `CommandCatalogDriftTest` should stay green.
**Warning signs:** `CommandCatalogDriftTest` failure after R4 plan — investigate if a spec was accidentally added or renamed.

### Pitfall 5: NSC CIDR Syntax Non-Existence
**What goes wrong:** Planner writes `<domain>192.168.0.0/16</domain>` expecting CIDR support.
**Why it happens:** Reasonable assumption, but NSC only supports exact hostnames and subdomain suffix matching.
**How to avoid:** Use the `useSecure` field approach (Option B) instead of trying to enumerate private ranges. The NSC cleartext base-config stays permissive; user controls via the Settings toggle.
**Warning signs:** Build warning or OkHttp `CLEARTEXT communication to ... not permitted` on LAN IPs even though they look like they should be allowed.

### Pitfall 6: DataStore Write Scope Cancellation (keep-screen-on toggle)
**What goes wrong:** Settings toggle writes through `rememberCoroutineScope()` — same-frame navigation cancels the write, slow flash loses it.
**Why it happens:** Recurring trap — see [[dinghy-compose-write-scope-cancellation]].
**How to avoid:** Route all DataStore writes through `AppContainer.writeScope` intent methods. Pattern is identical to `setBabystepEnabled`.
**Warning signs:** Keep-screen-on toggle reverts after navigating away.

### Pitfall 7: AdjusterPanel — clickable(onClick=null) vs enabled=false
**What goes wrong:** Wrapping the increment/decrement onClick in `if (controlsEnabled) { action() }` STILL installs a clickable handler — the tap is registered (ripples), then swallowed.
**Why it happens:** Conflating "silently ignores the tap" with "tap is not registered."
**How to avoid:** Use `Modifier.clickable(enabled = controlsEnabled) { action() }` or `onClick = if (controlsEnabled) action else null`. When `enabled = false` or `onClick = null`, no `PointerInputChange` is consumed and the ripple does not appear.
**Warning signs:** After the "fix," taps still show a ripple animation on the disabled stepper.

### Pitfall 8: UAST Crash on JDK 21 After Adding jvmToolchain(17)
**What goes wrong:** The Gradle daemon doesn't restart after adding `jvmToolchain(17)`, and the cached JDK-21 daemon keeps running lint.
**Why it happens:** `--daemon` mode reuses existing daemons; jvmToolchain change requires a new daemon.
**How to avoid:** Run the first lint task with `--no-daemon` after the toolchain change, or run `./gradlew --stop` first to kill running daemons.
**Warning signs:** UAST crash still appears after adding `jvmToolchain(17)`.
