<objective>
Close GAP 2 (UAT Check 8, MINOR): Fine-Tune does not reset to the Hub on same-destination re-selection.

Root cause (CONFIRMED in 17-UAT.md, build 7ed8e70 — NOT test drift): `ShellNavState.navigateTo()` early-returns at kt:90 when `target == dest`, BEFORE the Fine-Tune reset-to-Hub at kt:104-106 (`fineTuneGroup = null`). Hub→group is sub-nav WITHIN a single `Dest.FineTune` (tapping Motion only sets `nav.fineTuneGroup = MOTION`; dest stays `Dest.FineTune`). So re-entering Fine-Tune while already inside it (drawer tile over the Motion sub-page → `navigateTo(Dest.FineTune)` with `target == dest`) hits the early-return → the reset never fires → the stale MotionScreen renders. The RED instrumented test `FineTuneNavTest.reEnteringFineTune_opensHub_notStaleGroupPage` (kt:145-162) correctly catches this and is RIGHT — keep it. The SAME latent hole exists for Calibration (`calibrationRoutine` reset kt:98-100) and Macros (kt:93-96).

Fix (product, one spot): run the per-dest entry-reset side-effects even on a same-dest re-selection — handle `target == dest` by running the resets, then returning, instead of an unconditional early-return. One-spot change closes Fine-Tune + Calibration + Macros, making "Fine-Tune always opens the Hub" hold for EVERY entry path (REVIEW #6).

Purpose: re-entering a destination from its own drawer tile must always land on that destination's entry surface (the Hub / hub / bookmarked launcher), never a stale sub-page.
Output: a corrected `navigateTo()`; the existing RED instrumented nav test goes GREEN on flox.
