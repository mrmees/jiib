# Phase 15.1: Shape-Coded Status & Semantic Color - Research

**Researched:** 2026-06-05
**Domain:** Android theming internals (Kotlin) — semantic color assignment, shape-glyph rendering across the Compose↔Views hybrid, OKLCH color math, per-profile persistence
**Confidence:** HIGH (all findings verified against the live codebase + the sibling `theme_theory` source-of-truth; no external library research needed — this phase adds NO dependencies)

## Summary

Phase 15 already shipped the generative engine end-to-end and the substrate is in far better shape than a from-scratch read of CONTEXT.md would suggest. **The OKLCH↔sRGB conversion math already exists, ported and golden-tested, inside `Palette.kt`** (`hexToOklch`/`oklchToHex`, `internal` visibility). **The status trio already lives as three dedicated pool slots** that the generator re-orders by warmth, and **High-Contrast already force-overrides status to fixed RYG** (`Palette.generate` lines 415–433). **The per-profile override persistence, the `writeScope` durable-write path, and the Theme Editor per-slot UI all exist** and need *extension*, not invention. This is a wiring + semantics + docs phase, not a rebuild.

The four genuinely-new pieces of code are: (1) a **shape-glyph component** that renders octagon/triangle silhouettes in BOTH Compose and a classic `TextView`/RecyclerView row; (2) a **toolkit-agnostic N-series color helper** (mode×index→Color) consumed by the Views `GraphView` and future Compose lists; (3) an **OKLCH sequential ramp** for the bed-mesh view (replacing its sRGB `accent→surface2→stop` lerp), which can reuse the existing `Palette` OKLCH helpers; (4) **extending `poolOverrides` to the 3 status slots** through the already-built durable write path. Plus the **THEMING.md rewrite** (D-13) and a handful of **status-site rewirings** (the D-06 accent-leads supersession of Phase-15's nozzle=pool[0]).

**Primary recommendation:** Render the shape glyphs as a **single shared `VectorDrawable` resource per shape (octagon, triangle), tinted at the call site** — referenced from Compose via `painterResource()` + `ColorFilter.tint`, and from the console `TextView` via a tinted compound/inline drawable. This gives one geometry source of truth across the toolkit boundary. Put the N-series helper as a **pure free function on the resolved `ThemeTokens`** (`fun ThemeTokens.seriesColor(mode, i): Color`) so both toolkits reach it with zero new plumbing. Port the OKLCH ramp by **promoting the existing `Palette.oklchToHex`/`hexToOklch` helpers to a small reusable interpolation helper** rather than re-deriving matrices.

## Architecture Patterns

### System data flow (the resolved-token boundary is the spine)

```
User edit (Settings/Editor)            Persisted profile/global tuple
   │ setActive*(...)                        │ (DataStore: seed,dark,mode,shift,
   ▼                                        │  maxItems, poolOverrides{idx + status}, fs)
AppContainer  ──writeScope.launch──▶ ProfileStore.mutateActive / ThemePrefs.edit
   │  (process-lifetime scope — never a composition scope)
   ▼  seedTheme() flatMapLatest(active profile | global)
ThemeResolver.apply(tuple)
   │  synchronized: Palette.generate(seed,dark,mode,…)  → Generated (String hexes)
   │                TokenBridge.build(gen, overrides, fs) → ThemeTokens (baked sRGB Color)
   ▼
StateFlow<ThemeTokens>  ◀── the ONE unchanged boundary ──▶
   ├── Compose: DinghyTheme provides LocalTokens  → screens read t.accent / t.pool / t.seriesColor(...)
   └── Views:   ThemeableView.applyTokens(t)       → GraphView / BedMeshHeatmapView / ConsoleRowView
```

**Key insight:** the device NEVER does color math at paint time — `Palette.generate`+`TokenBridge.build` run ONCE per discrete theme change and cache the baked `Color`s on the `StateFlow`. The Adreno-320 render loop only reads cached `.toArgb()` ints. Any new helper (N-series, OKLCH ramp) must preserve this: compute-once, cache, read cheap.

### Pattern 1: Shape glyph as a shared `VectorDrawable` (RECOMMENDED, D-01)
**What:** One `res/drawable/ic_status_octagon.xml` and `ic_status_triangle.xml` (geometry only, `android:tint` left to the call site). Compose reads via `painterResource(R.drawable.ic_status_octagon)` with `ColorFilter.tint(t.stop)`. The console `TextView` row reads via `AppCompatResources.getDrawable(...)` → `DrawableCompat.setTint(d, t.stop)` → `setCompoundDrawablesRelativeWithIntrinsicBounds(d, …)` (leading icon) OR an `ImageSpan` if it must sit inline.
**When to use:** Any status site (Print-Status dot, Move axis letters, Stop/power buttons, console ERROR/WARNING rows).
**Why this over the alternatives:**

| Option | One geometry source? | Works in TextView/RecyclerView? | Grayscale-distinct silhouette control | Verdict |
|--------|---------------------|--------------------------------|--------------------------------------|---------|
| (a) Compose `Canvas`/`Path` + Android `Path` twin | ❌ two hand-kept path definitions | ✅ (Views path manual) | ✅ full control | Duplication risk — rejected |
| (b) Custom font glyph | ✅ (one font) | ✅ (it's text) | ⚠ glyph metrics/baseline fiddly; adds a font asset + build wiring; tint = text color only | Heavier; tinting & sizing fragile |
| **(c) Shared `VectorDrawable` (RECOMMENDED)** | ✅ one XML per shape | ✅ via `DrawableCompat`/compound drawable | ✅ author the silhouette directly | One source of truth, native tint API both sides |

**Silhouette-distinctness note (D-01 load-bearing):** author the octagon as a true 8-gon outline and the triangle as a filled/outlined triangle — they must differ at the *outer contour*, not just the inner ✕/! mark, so they survive grayscale + CVD. The inner mark (✕ for stop, ! for caution) is secondary redundancy. The existing JS reference uses Unicode `⯃`/`▲` in the HTML swatch preview only — do NOT ship Unicode glyphs as the production safety mechanism (font-dependent rendering, no silhouette guarantee on the Nexus 7's fonts).

### Pattern 2: N-series color as a pure extension on `ThemeTokens` (RECOMMENDED, D-05)
**What:** `fun ThemeTokens.seriesColor(mode: PaletteMode, i: Int): Color` returning the D-05 sequence element with infinite wrap. The mode is needed because the sequence differs per mode and `ThemeTokens` does not currently carry the mode (it carries baked colors only).
**When to use:** `GraphView.applyTokens` (replacing the bare `pool[i % size]`), any future Compose colored list.
**Where it lives:** a top-level/`object` function in `theme/` reading only `ThemeTokens` fields — toolkit-agnostic, no Android view imports, host-testable. **Both toolkits already hold a `ThemeTokens`** (Compose via `LocalTokens`, Views via `applyTokens`), so no new plumbing.
**Mode plumbing decision (for the planner):** `ThemeTokens` is baked-colors-only by design (the device-never-does-math rule). Two clean options — (1) add the active `PaletteMode` as a field on `ThemeTokens` (it's already a discrete input to `ThemeResolver`), or (2) detect mode from the baked tokens (Simple/HC collapse `pool` to text — detectable but fragile). **Recommend option (1): add `mode: PaletteMode` to `ThemeTokens`** — it's cheap, explicit, and the resolver already knows it. This is the cleanest expression of D-05 and keeps `seriesColor` a pure read.

```kotlin
// Source: derived from CONTEXT D-05 + ThemeTokens.kt (verified fields)
enum class PaletteMode { Colorful, Simple, HighContrast }

fun ThemeTokens.seriesColor(i: Int): Color = when (mode) {
    PaletteMode.Colorful   -> if (i == 0) accent else pool[(i - 1) % pool.size]
    PaletteMode.Simple     -> if (i % 2 == 0) accent else text
    PaletteMode.HighContrast -> {
        val seq = listOf(accent, stop, heat /*caution*/, go, text)
        seq[i % seq.size]
    }
}
```
(`heat` IS the caution token per ThemeTokens.kt:62–67. Guard empty `pool` as GraphView already does, CR-02.)

### Pattern 3: OKLCH sequential ramp by reusing the existing Palette helpers (D-11)
**What:** A perceptually-uniform ramp interpolated in OKLCH then converted to sRGB. The conversion already exists — **do not re-derive matrices.**
**Where it lives:** add to `theme/Palette` (host-pure, golden-test-friendly) a small ramp helper, OR a sibling `theme/OklchRamp.kt` that calls the now-already-`internal` `Palette.hexToOklch`/`oklchToHex`. The bed-mesh View calls it once per token change to bake a small lookup (e.g. 16–32 stops) into ARGB ints, then `lerpArgb`s between baked stops at paint time (keeps `onDraw` allocation-free and math-free — the Adreno-320 rule).
**The math is already in `Palette.kt` (verified):** `linToLab`/`labToLin` (the exact 3×3 OKLab matrices, lines 91–118), `sToL`/`lToS` (sRGB transfer), `hexToOklch`/`oklchToHex` (gamut-clamped 20-iter chroma reduction). **The planner's job is interpolation + stop selection, not color science.**
**Interpolation recipe:** convert both endpoints to OKLCH; lerp L, C, and H (H along the shorter arc); call `oklchToHex(L,C,H)` per stop (it already clamps out-of-gamut by reducing chroma). For a *sequential* (single-hue-family) ramp keep H roughly constant and ramp L; for a diverging ramp (low↔neutral↔high) pick two hue families off red/green.
**Stop selection (Claude's discretion, D-11):** the spec (§11) only mandates "perceptually uniform + off pure red/green." A defensible default: a **viridis-like blue→teal→yellow** sequential ramp (hues ~255°→~150°→~95°, L ramping ~0.45→0.85), or a **cividis**-style blue→yellow if CVD-safety is wanted for the heatmap too. Avoid red/green endpoints so a tall spot doesn't read as "FAILED" (the explicit D-11 rationale). Recommend deriving endpoints from neutral/accent-adjacent hues, NOT from the `stop` token.
**Golden-test angle:** because the ramp is pure OKLCH→sRGB, the planner can compute the reference stop values once (in JS or a notebook) and assert the Kotlin output bit-for-bit, exactly like `PaletteGoldenTest` does for the generator.

### Pattern 4: Status-slot overrides on the existing durable path (D-03)
**What:** Extend the override map to carry the 3 status slots alongside the integer pool indices.
**Current shape (verified):**
- `Profile.poolOverrides: Map<String, Long>` (String-keyed: pool index as decimal string `"0"`, `"1"`, … ARGB-as-unsigned-Long value).
- `ThemePrefs.ThemeTuple.poolOverrides: Map<Int, Long>`; wire form String→Long via `KEY_OVERRIDE_KEYS` (a `stringSet`) + per-key `pool_override_argb_<k>` longs.
- `AppContainer.setActiveOverride(active, index: Int, argb: Long?)` does the durable read-modify-write inside `mutateActiveProfile` (active) or `themePrefs.mutateOverrides` (global) — **both on `writeScope` (process-lifetime), never a composition scope** (the [[dinghy-compose-write-scope-cancellation]] fix is already applied here; status overrides MUST use the same method).
**Recommended extension:** reuse the SAME `Map<String, Long>` with **reserved string keys** `"stop"`, `"caution"`, `"go"` (the status slots are not integers, so they cannot collide with `"0".."63"` pool indices). `TokenBridge.build` then applies them after pool overrides: `stop = overrides["stop"]?.let{Color(it)} ?: bake(st.stop)`, etc. This keeps ONE map, ONE persistence path, ONE fail-safe sanitizer. The sanitizer (`sanitizeTuple`/`readOverrides`) already drops malformed entries per-key, so a junk `"stop"` value fails safe to the generated color.
**Alternative (rejected):** a separate `statusOverrides` map — more code, second persistence path, second sanitizer, no benefit.

### Anti-Patterns to Avoid
- **Doing color math in `onDraw`.** Both GraphView and BedMeshHeatmapView are explicitly allocation-free, math-free hot paths. The OKLCH ramp must bake stops on `applyTokens`, never compute per cell per frame.
- **Two divergent shape geometries** (Compose path + Views path). Use one drawable asset.
- **Persisting overrides on a composition scope.** [[dinghy-compose-write-scope-cancellation]] — a same-frame nav cancels the write on slow flash. Route through `AppContainer.writeScope` + one `dataStore.edit`/`mutateActive` (the existing pattern).
- **Shipping Unicode glyphs as the safety mechanism.** Font-dependent; no silhouette guarantee on the Nexus 7. Unicode is fine in the HTML reference only.
- **Re-porting the OKLab matrices.** They're already in `Palette.kt`, golden-tested. Reuse `hexToOklch`/`oklchToHex`.

## Common Pitfalls

### Pitfall 1: D-06 supersession missed — nozzle stays pool[0]
**What goes wrong:** Phase-15 wired nozzle=`pool[0]`/`directional.temperature` (GraphView trace 0 = pool[0], PrintStatus nozzle readout = pool[0]). D-06 changes nozzle to **accent**. If the planner only ADDS the N-series helper without re-binding, the nozzle trace and readout stay pool[0] and contradict the locked decision.
**Why it happens:** The Phase-15 code + KDoc explicitly says "trace i = pool[i % size]" — it reads as correct.
**How to avoid:** D-05/D-06 means trace 0 = `seriesColor(0)` = **accent** in all modes; trace 1 = pool[0] (bed), trace 2 = pool[1] (chamber). The PrintStatus nozzle readout must ALSO resolve to accent (stable identity — same channel same color, per the Integration Points note). Grep every `pool[0]` / `directional.temperature` consumer and re-point.
**Warning signs:** nozzle trace is not the accent hue; nozzle readout color ≠ nozzle trace color.

### Pitfall 2: `directional` re-tag breaks dual-tagged consumers (D-07)
**What goes wrong:** `Directional{temperature, xy, z}` currently derives `temperature` from the warmest top-3 pool hue. D-07 reconceives `temperature→accent`, `xy→pool[0]`, `z→pool[1]`. Move screen reads `directional.xy`/`directional.z` (D-08); if `directional` is re-derived in `Palette`/`TokenBridge`, Move's jog-pad/Z colors shift.
**Why it happens:** `directional` is a STORED field (verified: `ThemeTokens.directional: Directional`, built in `TokenBridge` from `gen.directional`, itself computed in `Palette.generate` via warmth-sorted top-3). It is NOT a derived alias today.
**How to avoid (Claude's discretion per CONTEXT):** Decide derived-alias vs stored. **Recommend: keep `directional` a stored field but redefine its derivation** so `temperature=accent`, `xy=pool[0]`, `z=pool[1]` — this keeps Move/D-08 reading `directional.xy`/`.z` unchanged in shape while the VALUES become pool[0]/pool[1] (exactly D-08's intent). Confirm Move/PrintStatus read `directional.*`, not raw `pool` indices, so the single re-derivation point covers them. In Simple/HC the generator already collapses directional to `txt` — confirm accent-leads still holds (temperature should be accent even in mono, since accent survives all modes per D-05).
**Warning signs:** Move jog-pad color ≠ pool[0]; nozzle (temperature) ≠ accent after a reseed.

### Pitfall 3: Shape glyph in the console RecyclerView row
**What goes wrong:** `ConsoleRowView` is a bare `TextView` subclass; it has no Compose. A naive "add a Compose icon" approach can't reach it.
**Why it happens:** Easy to forget one of the four status sites is classic Views.
**How to avoid:** Use the shared `VectorDrawable` + `setCompoundDrawablesRelativeWithIntrinsicBounds` (leading icon) tinted via `DrawableCompat.setTint(t.stop/t.heat)` in the row bind, sized to the `fsSp`-scaled text. Only ERROR (octagon) and WARNING (triangle) rows get a glyph (D-02); NORMAL/DEBUG/ACTION get none.
**Warning signs:** glyph renders in Compose status sites but not in the console scrollback.

### Pitfall 4: Font sizing the new glyph/editor text too small
**What goes wrong:** [[dinghy-font-sizes-too-small]] — recurring. New glyph + status-slot editor labels get sized too small.
**How to avoid:** size glyphs and any new editor text via `fsSp(baseSp, t.fs)` (floor 15sp metadata, 17–18sp body, 20–22sp titles). Glyph intrinsic size should track the adjacent status text's `fsSp`.

### Pitfall 5: OKLCH ramp does math per cell
**What goes wrong:** Computing `oklchToHex` per heatmap cell per frame would tank the Adreno-320 fill rate (50×50 grid × 20-iter gamut search).
**How to avoid:** Bake a small ARGB lookup (e.g. 32 stops) once in `applyTokens`; `onDraw` indexes/`lerpArgb`s between baked stops. Mirrors how the current ramp already works (baked endpoint ints + `lerpArgb`).

### OKLCH ramp baking (reusing existing Palette helpers)
```kotlin
// Source: reuse Palette.hexToOklch/oklchToHex (already internal + golden-tested in Palette.kt)
// Build N baked sRGB stops once on token change; lerp between baked ints in onDraw.
fun bakeRamp(lowHex: String, highHex: String, stops: Int): IntArray {
    val a = Palette.hexToOklch(lowHex); val b = Palette.hexToOklch(highHex)
    return IntArray(stops) { k ->
        val t = k.toDouble() / (stops - 1)
        val L = a.L + (b.L - a.L) * t
        val C = a.C + (b.C - a.C) * t
        val H = lerpHueShortArc(a.H, b.H, t)      // shorter-arc hue lerp
        bakeHexToArgb(Palette.oklchToHex(L, C, H))
    }
}
```
