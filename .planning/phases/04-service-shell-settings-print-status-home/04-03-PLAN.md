<objective>
Bring the app to life: a process-held service-locator (`AppContainer`), an `Application`
(`DinghyApp`) that owns it plus the real DataStore files, and a started **foreground service**
(`specialUse`) that assembles and runs the Phase-2 Moonraker spine from the persisted
`ConnectionStore` config — surviving Activity recreation and screen-off (SHELL-03, D-01..D-03).
Saving a new connection rebuilds the session cleanly (D-03). This is the load-bearing wave:
every Wave-3 screen reads its state from the container the service publishes into.

Purpose: The connection now belongs to the OS, not the Activity — rotation/config-change/screen-off
no longer drop it; the user's saved config (04-01) becomes the live source replacing DevConfig.

This revision nails down three cross-plan seams the review flagged:
- **#1 SessionControl:** the UI (Splash 04-05, Stop 04-06) reaches reconnect/restart ONLY through a
  narrow `SessionControl` interface (`requestReconnectNow()`, `restartFirmware()`, `restartHost()`).
  The raw `MoonrakerSession` is NEVER exposed.
- **#6 Atomic spine publication:** all live spine references live in ONE immutable `SpineHandle`
  published via a single `StateFlow<SpineHandle?>`. A rebuild swaps the whole handle in one
  assignment so partially-swapped flow/session refs are unrepresentable.
- **#3 Rotation continuity:** the handle carries a monotonic `sessionInstanceId`; the rotation gate
  asserts CONTINUITY of the same id across Activity recreation (not the absence of a transition,
  which a harness republish could spoof).

Output: manifest perms + service + Application registration, `DinghyApp`, `AppContainer`,
`SpineHandle`, `SessionControl`, `MoonrakerService`, a JVM config-rebuild-seam test, an AppContainer
unit test, and an instrumented rotation-survival test.
</objective>
