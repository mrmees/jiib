  <behavior>
    Pure mapping `fractionFromX(x: Float, barWidthPx: Float): Float` (top-level, file-private-but-testable
    — make it `internal` so the test module sees it):
    - Test: fractionFromX(0f, 100f) == 0f (left edge → start fraction)
    - Test: fractionFromX(100f, 100f) == 1f (right edge → end fraction)
    - Test: fractionFromX(50f, 100f) == 0.5f (midpoint)
    - Test: fractionFromX(-10f, 100f) == 0f and fractionFromX(150f, 100f) == 1f (clamped to 0..1)
    - Test: fractionFromX(50f, 0f) == 0f (zero/un-measured bar width returns 0f, never NaN/divide-by-zero)
    - Test (tap == drag invariant): for the same x and barWidth, the value a tap produces equals the
      value a drag-to-that-x produces — i.e. both paths funnel through fractionFromX, so asserting the
      mapping is deterministic per x is sufficient.
  </behavior>
  <action>
    G-3 (tap-to-set, race-free). The current single `detectDragGestures(onDragStart = …)` never fires
    on a zero-movement tap — Compose's drag detector requires touch-slop movement before onDragStart,
    so a pure tap is dropped. Replacing it with a SECOND `pointerInput`/`detectTapGestures` reintroduces
    the dual-pointerInput pointer-stream race the prior WR-01 fix removed. Use ONE coordinated detector
    in the existing single `.pointerInput(range, step)` block: replace `detectDragGestures` with
    `awaitEachGesture { … }` using `awaitPointerEventScope`:
      1. `val down = awaitFirstDown(requireUnconsumed = false)` — set the value immediately from
         `down.position.x` (this is what makes a zero-movement tap register). Consume the down so the
         enclosing scaffold/scroll can't steal it.
      2. Loop `awaitPointerEvent()`; for each change still pressed, set the value from its
         `position.x` and consume it. Exit the loop when all pointers are up.
    Every value write goes through a single `setFromFrac` that calls the existing `set(...)`:
    `set(range.start + fractionFromX(x, barWidthPx) * span)`. Extract `fractionFromX` as an `internal`
    top-level function (NOT a local lambda — it must be unit-testable per the behavior block) and
    delete the old local `setFromX`, routing both the down-set and the move-set through it. This gives
    a tap at x and a drag to x an identical result and a single pointer consumer (no race).

    Keep it keyboard-free: do NOT add any TextField/BasicTextField/KeyboardType — the ban in the KDoc
    and docs/ui_design/CLAUDE.md still holds. The steppers and onValueChange/onApply contract are
    unchanged.

    G-2 (shared width). The fill bar lives in the scaffold Field with `.padding(24.dp)`; the
    −/+/Cancel/Apply group lives in the gutter Column with `.padding(horizontal = 16.dp, …)`. They
    therefore present different effective widths. Make the bar and its own button group share one
    inset: set BOTH the Field bar's horizontal padding and the gutter Column's horizontal padding to
    the SAME value (use 16.dp on the bar's `.padding(...)` — keep its vertical 24.dp if the scaffold
    needs vertical breathing room, i.e. `.padding(horizontal = 16.dp, vertical = 24.dp)` — and keep
    the gutter at `horizontal = 16.dp`). Do not introduce a hardcoded absolute bar width (LAYOUT.md
    non-negotiable #3: ratio/inset only, no fixed px width); the goal is a shared LEFT edge + width,
    achieved by a shared horizontal inset, not a magic dp width. If Field and Gutter are separate
    scaffold regions whose intrinsic widths already match (both full-width), the equal horizontal inset
    is sufficient — verify visually in Task 4.
  </action>
