<objective>
Close gaps G2 (HIGH) and G3 (MED, same root). After a Klipper FIRMWARE_RESTART or printer.cfg reload,
Klipper emits `notify_klippy_ready` over the EXISTING (still-open) Moonraker websocket. Today
`MoonrakerSession` routes that notification only to `store.onKlippyMethod()` (which updates KlippyState) —
it NEVER re-runs the handshake. So the objects/subscribe registration is lost, temps/positions freeze
while gcode still dispatches, and because the persistent FGS keeps the dead session alive, reopening the
app does NOT recover. Only a force-stop fixes it. The constant `NOTIFY_KLIPPY_READY` is defined in
JsonRpc.kt but is otherwise referenced only in a code comment. Confirmed live on flox during Phase-5 UAT.

G3 is closed by the same change: the 05-03 one-shot reads (temperature_store backfill, configfile
`min_extrude_temp` / `max_extrude_only_distance`) run only inside `runHandshake()` at initial connect, so
they go stale across a config reload. The G2 re-handshake MUST re-run `runHandshake()` in full — re-subscribe
AND re-run the one-shot reads — not merely re-subscribe.

Purpose: The FGS-held session must self-heal across a Klipper restart so the touchscreen recovers without
user intervention, and the cold-extrude / temp-graph config values stay accurate after a printer.cfg edit.

Output: A klippy-ready re-handshake path in MoonrakerSession plus a faithful test (per the mock-vs-reality
lesson) that injects a notify_klippy_ready frame on a live socket and proves the handshake re-runs.
</objective>
