## Summary

This is a **rendering-seam + integration** phase, not a new-library phase. Nothing new is installed; the
work is authoring one custom asset and wiring a runtime-tinted/runtime-gradient composable across five
existing surfaces. The single real unknown (D-04) is **already solved precedent in this repo**:
`designsystem/ColorWheel.kt` is a Compose `Canvas` control that draws with a cached `Brush` gradient and
explicitly renders "a literal-hue dot (the data-color carve-out), ringed by a token-chromed outline
(THEME-01)" (ColorWheel.kt:128-129) — which is *exactly* the filament-band-plus-keyline pattern D-05
describes. The Adreno-320 caching discipline is already established there (`rememberHueSweep()` caches
the gradient; ColorWheel.kt:68, 184-188).

**The cleanest seam is NOT to render a gradient inside a VectorDrawable.** Android VectorDrawable cannot
take a runtime gradient (its `<gradient>` is static XML), and `DinghyIconView`'s `Icon(painter, tint)`
contract is a single flat tint (DinghyIconView.kt:63-69). The recommended approach (Q1, Option C) is a
**single dedicated `@Composable SpoolGlyph(...)`** that owns BOTH regions: it draws the **body** from the
custom VectorDrawable via a token-tinted `Icon`/`painterResource` (reusing the existing flat-tint
contract for the neutral body), and draws the **band + keyline** in a small overlaid Compose `Canvas`
using `Brush.linearGradient` (multi-color), `SolidColor` (single color), or nothing (empty-spool
fallback). The two layers share one fixed coordinate frame because the VectorDrawable's viewBox and the
Canvas size are both pinned to the icon-box `sizeDp` — band geometry is authored as fixed fractions of
that box.

**Primary recommendation:** Author a side-view spool VectorDrawable whose **body/flanges** are stroke-led
white paths (per `nozzle.xml`) AND that **excludes** the band region (the band is drawn entirely by the
Canvas overlay, never by the vector). Build one `SpoolGlyph(swatches: List<Color>, bodyTint: Color,
keyline: Color, sizeDp: Dp)` composable. Route all five surfaces through it. The drawer tile (D-06.2)
gets a `DrawerTileSpec.glyph: (@Composable (tint) -> Unit)?` escape hatch so exactly one tile renders the
custom composable while the rest stay `symbol: String`-driven. **Expect and pre-plan the
`DinghyIconsTest` drift-guard breakage (Q5).**

### Pattern: literal-data-color + token keyline (the D-05 precedent already in-repo)

`ColorWheel.kt:128-137` already implements the exact "true color + neutral framing" idea this phase
needs, on the same hardware budget:

```kotlin
// Source: app/src/main/java/works/mees/dinghy/designsystem/ColorWheel.kt:128-139
// The handle: a literal-hue dot at the current angle (the data-color carve-out), ringed by a
// token-chromed outline (THEME-01). ...
val rad = Math.toRadians(hue.toDouble())
val hx = cx + (ringR * cos(rad)).toFloat()
// (draws a literal-color fill, then a token-color stroke around it)
```

The band is the spool-glyph analogue of that handle dot: literal filament color fill, token keyline
stroke. Reuse the mental model and the caching discipline.

### Pattern: cache the brush, not per-frame allocation (Adreno-320 discipline)

`ColorWheel.kt:68 + 184-188` caches its gradient brush across frames via `remember`. The spool band is
**static** (no animation — root CLAUDE.md "NO continuous animation" on Adreno 320), so the band draws
once per recomposition and only when the resolved swatches change. Build the `Brush.linearGradient`
inside the Canvas `DrawScope` (it's cheap and the glyph is small/static) or `remember` it keyed on the
swatch list if the same glyph is drawn many times in a list. At launcher/drawer/shortcut sizes there is
ONE instance per surface — allocation cost is negligible.

### Anti-Patterns to Avoid
- **Baking `<gradient>` into the VectorDrawable XML.** It's static; filament colors are dynamic data.
  Explicitly forbidden by D-04. The band must be Canvas-drawn.
- **Forcing the gradient through `DinghyIconView`/`Icon(tint=…)`.** That contract is a single flat
  `Color` (DinghyIconView.kt:42, :67). A gradient is "beyond this view's flat-tint contract"
  (CONTEXT/DinghyIcons note). Do not try to extend `tint` to a `Brush` on the shared view — make a
  dedicated `SpoolGlyph` instead, leaving `DinghyIconView` untouched.
- **Drawing the band region inside the body vector AND over it.** Double-drawing the band area causes
  a visible seam where the token-tinted vector band peeks through the Canvas band. Author the vector to
  **exclude** the band region entirely (body/flanges only); the Canvas owns the band exclusively.
- **Tinting the whole glyph with the filament color.** Rejected in discussion (filament-only, D-02).
- **Clamping the color for legibility (`brandTint`).** Rejected (D-05) — distorts true color. Keyline only.

## Common Pitfalls

### Pitfall 1: The `DinghyIconsTest` drift-guard breaks the build (SC6 risk)
**What goes wrong:** `DinghyIconsTest.registryDrawableEntries_areOnlyTheCustomKeepers()` (lines 99-111)
asserts the ONLY `IconRef.Drawable` entries in `DinghyIcons.all` are exactly `{"nozzle","heat_bed"}`.
Flipping `LauncherSpool` from `Ligature("database")` to `Drawable(R.drawable.spool)` (D-01) adds a
third drawable-backed entry → the test fails RED, and SC6 ("unit tests green") cannot pass.
**Why it happens:** the guard was authored in 18.1 to catch *un-flipped* drawables; it has no allowance
for an intentionally-added custom printer-domain drawable (which is precisely what 18.1's own
icon-source policy SANCTIONS — DinghyIcons.kt:16-21 lists "spool" as a sanctioned custom glyph).
**How to avoid:** update the expected keeper set to `setOf("nozzle","heat_bed","launcher_spool")` (or
whatever `alternate` the flipped entry keeps) **in the same plan/wave** that does the flip. Also update
the test's KDoc, which currently enumerates the keepers. This is a *planned* edit, not a surprise.
**Warning signs:** any plan that flips `LauncherSpool` without a paired `DinghyIconsTest` edit.

### Pitfall 2: `iconRef_isUnique` collision is silently RESOLVED by the flip (verify, don't assume)
**What goes wrong:** `iconRef_isUnique_acrossAllEntries()` (line 67) already flagged a historical
`Progress`(`donut_large`) ↔ `LauncherSpool` collision concern (DinghyIcons.kt:53-57). `LauncherSpool`
currently uses `database` (distinct). After the flip it becomes a `Drawable` — a *new* IconRef value,
still unique. **No action needed**, but confirm the flip doesn't accidentally reuse an existing resId
or alternate. The `alternate_isUnique` test (line 43) still guards the handle string.
**How to avoid:** keep `alternate = "launcher_spool"` (or pick a new unique handle); don't reuse a resId.

### Pitfall 3: Body/band misalignment across the two layers
**What goes wrong:** the token-tinted body (VectorDrawable, sized in `dp`) and the Canvas band (sized in
`px` within the same box) drift if their coordinate frames aren't pinned identically.
**Why it happens:** `DinghyIconView` sizes the drawable painter via `.size(sizeDp)` (DinghyIconView.kt:66);
a separate Canvas must `fillMaxSize()` the *same* box and express band geometry as fractions of
`size.width`/`size.height` (as `ColorWheel.kt:114-118` derives everything from `size`).
**How to avoid:** the `SpoolGlyph` composable wraps both in ONE `Box(Modifier.size(sizeDp))`; the body
`Icon` and the band `Canvas` both `fillMaxSize()`. Author the vector viewBox (e.g. 96×96) and define
band edges as the same 0..1 fractions in the Canvas math. Document the band rectangle once.

### Pitfall 4: Gradient brush ignores the path bounds
**What goes wrong:** `Brush.linearGradient` with default `start`/`end` spans the whole DrawScope, not the
band path's local bounds — the two-stop transition can land off-band, making the band look like a flat
single color.
**Why it happens:** the brush coordinate space is the draw layer, not the clipped path.
**How to avoid:** pass explicit `start = Offset(bandLeft, …)` / `end = Offset(bandRight, …)` matching the
band rectangle (the gradient direction is Claude's discretion per CONTEXT). Then `drawPath(bandPath,
brush=…)` clips the brush to the band geometry. `ColorWheel.kt:184-188` shows the explicit-stops pattern.

### Pitfall 5: Empty-spool fallback shows a recolored placeholder instead of a real empty spool
**What goes wrong:** drawing the band region in a dead token (the old "tint the whole glyph dead")
instead of OMITTING the band reads as a greyed icon, not an honest empty spool.
**Why it happens:** instinct to always draw something.
**How to avoid:** when `swatches.isEmpty()` the Canvas draws NOTHING in the band region (D-03); only the
neutral body renders. *The presence/absence of the band IS the "filament loaded" signal* (CONTEXT
specifics). Optional: a faint token keyline outline of the empty band area is acceptable but not
required — verify on-device.

### Pitfall 6: `parseNormalizedHex` is `private` in SpoolScreen
**What goes wrong:** `SpoolGlyph` needs hex→`Color`; the existing helper is `private`
(SpoolScreen.kt:502).
**How to avoid:** promote it to an internal top-level util (e.g. in the spool package or a small color
util) and have both `SpoolScreen` and `SpoolGlyph` call it — don't duplicate the parse logic.

### The dedicated reactive glyph (recommended seam — Option C)
```kotlin
// Source pattern: DinghyIconView.kt:63-69 (body) + ColorWheel.kt:113-139 (band+keyline Canvas).
@Composable
fun SpoolGlyph(
    swatches: List<Color>,     // 0 = empty spool, 1 = solid, 2+ = two-stop gradient (take 2)
    bodyTint: Color,           // neutral role token (D-02)
    keyline: Color,            // neutral role token (D-05)
    sizeDp: Dp,
    modifier: Modifier = Modifier,
    contentDescription: String? = null,
) {
    Box(modifier.size(sizeDp)) {
        // Body/flanges — existing flat-tint contract (token, NOT reactive).
        Icon(painterResource(R.drawable.spool), contentDescription, Modifier.fillMaxSize(), tint = bodyTint)
        // Band — runtime brush over a fixed band path (fractions of the same box).
        Canvas(Modifier.fillMaxSize()) {
            if (swatches.isEmpty()) return@Canvas         // D-03 empty spool — band omitted
            val bandPath = spoolBandPath(size)            // authored band rect, matches the vector body
            val brush = when (swatches.size) {
                1 -> SolidColor(swatches[0])
                else -> Brush.linearGradient(             // D-04 two-stop; explicit stops to band bounds
                    0f to swatches[0], 1f to swatches[1],
                    start = Offset(bandLeft(size), 0f), end = Offset(bandRight(size), 0f),
                )
            }
            drawPath(bandPath, brush)
            drawPath(bandPath, keyline, style = Stroke(width = keylineWidth(size)))  // D-05 keyline
        }
    }
}
```

## Open Questions

1. **Where does the active print's `filament_colors[0]` live at render time?**
   - What we know: `FilePreviewMetadata.filamentColors` is the parsed source (PrintMetadata.kt:51-52,
     :94); `PrintStatusScreen` collects `container.printMetadata` (a `PrintMetadata`, which has NO
     colors) at :135.
   - What's unclear: whether a `FilePreviewMetadata` for the *currently printing* file is already
     reachable in `PrintStatusScreen`, or whether the gcode-fallback path needs a small flow
     thread-through.
   - Recommendation: the planner should grep `AppContainer` for a flow carrying the active file's
     `FilePreviewMetadata` (the Files preview path parses it). If absent for the active print,
     scope a tiny "active-file colors" exposure into the plan — but note Spoolman-first (D-07) covers
     the common case and the empty-spool fallback covers the rest, so this is a fallback-quality issue,
     not a blocker.

2. **Promote `parseNormalizedHex` or add a shared color util?**
   - What we know: it's `private` in SpoolScreen.kt:502; `SpoolGlyph` needs it.
   - Recommendation: promote to `internal` top-level (spool or designsystem package); have SpoolScreen
     call the promoted version. Cheap, avoids duplication.

3. **Keyline width + gradient direction.** Claude's discretion (CONTEXT). Recommend authoring the
   keyline at ~1–1.5dp-equivalent (fraction of box) so it reads at launcher-tile size without dominating;
   horizontal gradient (flange-to-flange) reads most naturally for a side-view spool. Verify on-device.
