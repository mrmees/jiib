# Phase 18.1: Icon System Conformance - Context

**Gathered:** 2026-06-07
**Status:** Ready for planning

<domain>
## Phase Boundary

Apply Phase 18's icon-**source** policy across the WHOLE app: every icon is a real Material
Symbol (font ligature, or an official Google vector verbatim where the bundled font lacks the
glyph) **except** the genuinely-custom printer-domain glyphs Material Symbols has no equivalent
for. Refresh the bundled Material Symbols Outlined font to a current cut, convert the remaining
hand-traced "Material-Symbol-wannabe" drawables to their bucketed Material Symbol, and mop up the
cosmetic KDoc doc-link warnings.

**This is icon SOURCE/form conformance** — *which* glyph, *from where*. It is NOT the per-screen
icon-call-site **tokenization** coverage (routing call sites through `DinghyIcons` tokens +
`stringResource`). That stays in Phase 22's deferred backfill (D-03). Changing a raw call site's
glyph SOURCE (drawable → font ligature / official vector) is in scope here even if that call site
is not yet routed through the `DinghyIcons` registry — see D-09.
</domain>

<decisions>
## Implementation Decisions

### Font refresh & sizing
- **D-01:** Refresh `app/src/main/res/font/material_symbols_outlined.ttf` to a current Material
  Symbols **Outlined** cut. Source: Google's `material-design-icons` / fonts.google.com variable
  font. Keep it a **variable** font (do NOT instance) — call sites render at both `opsz` 24 and 48
  per the bucket, and the variable file carries the full `opsz` range.
- **D-02:** Locked axis settings: **FILL 0 / wght 400 / GRAD 0** (from `material-icon-bucket.json`;
  matches every bookmark). The render layer selects `opsz` per call site.
- **D-03:** **Ship the full refreshed font now** (~10.6 MB). Subsetting is **deferred to Phase 22**
  ship-hardening, where R8/APK-size work already lives. The `tools/subset-symbols` referenced in the
  `DinghyIcons` KDoc does **not exist yet** — it is aspirational; do NOT build it this phase. When
  Phase 22 does subset, source the glyph list from `material-icon-bucket.json` (the app-wide
  intended-glyph superset), NOT `DinghyIcons.all` (which would break the moment a Phase-22 call site
  uses a bucketed glyph not yet in the registry).
- **D-04:** After the refresh, **re-verify every existing `IconRef.Ligature` name still resolves**
  in the new font (`DinghyIconsTest` + on-device spot check). Several glyphs that previously had to
  ship as vectors (e.g. `detector`, `text_select_move_forward`) should become ligatures once the
  font is current.

### Status shape glyphs (D-01/D-02 shape-coded safety system)
- **D-05:** **Stop/danger → `disabled_by_default`** (square + ✕; bucket note "STOP / red").
  **Caution → `warning`** (triangle + !; bucket note "WARNING, yellow"). Replaces the hand-traced
  `ic_status_octagon.xml` / `ic_status_triangle.xml`.
- **D-06:** This **drops the literal octagon / stop-sign silhouette**. Owner explicitly accepted:
  square+✕ vs triangle+! remain **shape-distinct in grayscale/CVD**, so the shape-coded safety
  redundancy survives — just not as an octagon. **Roadmap SC-2 must be relaxed** from "preserve the
  *exact shape* semantics (octagon)" to "preserve **shape-DISTINCT** safety coding (square+✕ vs
  triangle+!)" so the verifier does not flag this as a criterion miss.
- **D-07:** **Views caveat (researcher/planner):** the status glyphs render in the **classic-Views
  console row** via `DrawableCompat.setTint` (ADR-0001 — console is Views, not Compose). For Views
  call sites, the cleanest source-conformant path is an **official Google vector drawable**
  (`disabled_by_default` / `warning`, path data verbatim) — the policy explicitly allows official
  vectors — rather than forcing a Material-Symbols-font-ligature-in-TextView. Compose call sites use
  the font ligature. RESEARCH this rendering split.

### Post-research amendments (owner-confirmed 2026-06-07, supersede where noted)
Research inspected the actual font binary (`fonttools`) and surfaced three corrections; owner ruled:

- **D-13 (amends D-01/D-03):** **Retain the bundled `material_symbols_outlined.ttf` (v2.944) — do NOT
  swap the binary.** Inspection proved v2.944 is already a full variable cut with the correct axes
  (FILL 0-1 / wght 100-700 / GRAD -50..200 / opsz 20-48) and already carries **every** glyph this
  phase needs (all 13 D-08 targets + all 35 existing ligatures resolve). A refresh is a correctness
  no-op and a 10.6 MB binary swap is pure risk. **D-01's literal "refresh to a current cut" is RELAXED
  to "verify the bundled font is a current variable cut that resolves every needed glyph, and record
  provenance (v2.944 retained, verified sufficient)."** The verification is the deliverable, not a new
  binary. (Roadmap SC-1 wording to be read through this lens — verifier must not flag a missing refresh.)

- **D-14 (amends D-05/D-06/D-09):** **Rename the registry token `StatusOctagon` → `StatusStop`** (KDoc
  citing D-06). Post-D-06 the glyph is `disabled_by_default` (square+✕), so the `Octagon` name lies.
  Mechanical rename across its call sites (compiler catches misses).

- **D-15 (amends D-09 — the "four" was non-exhaustive):** The D-09 registry source-flip set is **SIX**
  entries, not four. In addition to `StatusStop`(was StatusOctagon)/`BabystepCompress`/`BabystepExpand`/
  `PressureAdvance`, the registry-backed **`Increase` (→ `add`)** and **`Decrease` (→ `remove`)** entries
  are also `IconRef.Drawable(...)` today and MUST flip to `IconRef.Ligature(...)` or the phase
  under-delivers. The `DinghyIconsTest` drift-guard (Wave-0) asserts all six are `IconRef.Ligature` and
  the remaining `IconRef.Drawable` ⊆ {Nozzle, HeatBed}.

- **D-16 (amends D-11):** Most `[AppContainer]` KDoc links resolve (imports present) — but **Codex found
  ONE genuine exception**: `preview/PrintStatusPreviews.kt:35` uses `[AppContainer]` in prose with **no
  AppContainer import** in that file → unresolved. So the KDoc cleanup is **FIVE edits**: `[DinghyPreviews]`
  → `[Nexus7Previews]` (×3) + the stale `[PrintStatusThemeMatrix]` → `[PrintStatusStateMatrix]`, PLUS
  de-bracket the `PrintStatusPreviews.kt:35` `[AppContainer]` → `AppContainer` (it is descriptive prose,
  not a real cross-ref; dropping brackets clears the warning without an unused import). `[AppContainer]`
  links in OTHER files are left untouched (they resolve). Re-grep after edits to confirm none remain.

<code_context>
## Existing Code Insights

### Reusable Assets
- **`DinghyIcons` registry + `IconRef` sealed type** already model `Ligature` vs `Drawable` sources —
  conversion of the registry-backed entries (D-09) is a one-line source flip per entry, plus removing
  the entry from the drawable-backed group.
- **`material-icon-bucket.json`** is effectively a pre-made decision log — no glyph hunting needed.
- **`MaterialSymbol.kt`** already renders ligatures from the bundled font with the locked axes; the
  font refresh (D-01) is a binary swap + axis re-confirm, not new render code.

### Established Patterns
- **Hybrid toolkit (ADR-0001):** Compose for most surfaces; **classic Views** for Files / temp graph /
  **Console scrollback**. The status glyphs live in the Views console row (`DrawableCompat.setTint`) →
  drives the D-07 official-vector-for-Views split.
- **White-stroke-tinted-at-call-site:** all current glyph drawables draw white and are recolored via
  semantic token at the call site (THEME-01). Font ligatures are tinted the same way (`Icon(tint=…)`),
  so the conversion preserves the theming contract.
- **`fsSp(baseSp, t.fs)`** is the icon/text sizing scale (memory `dinghy-font-sizes-too-small`).

### Integration Points
- `DinghyIcons.kt` (registry flips), the raw call sites enumerated by D-08's grep, `MaterialSymbol.kt`
  (font asset), and the Views console row (status glyphs). Each converted drawable file is deleted
  once its single/few call sites no longer reference it.
</code_context>
