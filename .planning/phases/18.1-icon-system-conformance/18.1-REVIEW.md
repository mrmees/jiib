# Phase 18.1: Code Review Report

**Reviewed:** 2026-06-07T18:29:48Z
**Depth:** standard
**Files Reviewed:** 13
**Status:** issues_found

## Summary

Phase 18.1 swaps a set of hand-traced / redundant local vector drawables for canonical Material
Symbols — rendered either as font ligatures (via `MaterialSymbol` / `DinghyIconView`) or, at the one
classic-Views call site that can't use a font ligature on minSdk-23, as two OFFICIAL Google vector
drawables (`disabled_by_default.xml`, `warning.xml`). I reviewed the swap for glyph-name correctness,
tofu risk, preserved accessibility, preserved theming/tinting, and the correctness of the ligature
gate tool.

The core mechanics are sound. I independently **ran `tools/verify_ligatures.py` against the committed
font** — it reports `48 needed, 3953 ligatures in font, missing: []` (exit 0), so every flipped glyph
name resolves as a real ligature in the bundled v2.944 font. No tofu risk. I also verified:
- Every `IconRef.Ligature(...)` name in `DinghyIcons` (42 unique) is covered by the gate's `NEEDED`
  set, plus the six screen-local ligatures (`detector`, `lock`, `lock_open_right`, `warning`,
  `arrow_upward`, `arrow_downward`) — the gate is not stale.
- All deleted drawables (`detector`, `expand`, `compress`, `add`, `remove`, `arrow_upward`,
  `arrow_downward`, `ic_status_*`, `ic_lock_*`, `babystep*`) have **zero** dangling `R.drawable.*`
  references in main or test sources, and the files are physically gone.
- The only remaining `IconRef.Drawable` registry entries are the two D-10 keepers (`nozzle`,
  `heat_bed`); the drift-guard test will go GREEN.
- `StatusOctagon` is fully renamed to `StatusStop` (no stale references, including the build-breaker
  the Codex review caught at PrintStatusScreen.kt:971).
- The `output_circle` registry duplicate is the only duplicated ligature and is explicitly allow-listed
  in `DinghyIconsTest.iconRef_isUnique_acrossAllEntries`.

The findings below are a real accessibility regression introduced by the swap (WR-01), and two
documentation defects from imprecise find-replace edits (WR-02 is a mislabeled KDoc cross-link; WR-03 a
KDoc/code drift). No blockers.

## Warnings

### WR-01: Decorative-icon swap leaks raw ligature name to TalkBack (a11y regression)

**File:** `app/src/main/java/works/mees/dinghy/ui/move/MoveScreen.kt:449-460`,
`app/src/main/java/works/mees/dinghy/ui/screen/ThemeEditorScreen.kt:548-553` and `:633-638`

**Issue:** The swapped sites in `MoveScreen.StatusShape`, `ThemeEditorScreen.DataSwatch`, and
`ThemeEditorScreen.StatusSlotSwatch` now render via the **bare `MaterialSymbol`** primitive. Before the
swap these were `Icon(painter = …, contentDescription = null)` — decorative, so TalkBack spoke nothing.
`MaterialSymbol` renders the ligature name as a Compose `Text` with **no semantics override** (see
`MaterialSymbol.kt:37-43` — it is a plain `Text(text = name, …)`), so TalkBack will now announce the
raw glyph name: "warning", "lock", "lock open right", "disabled by default". That is a behavior change
for the THREE Phase-18 a11y surfaces, and it contradicts the phase intent ("preserved
content-descriptions/accessibility").

The project already has the correct primitive for this: `DinghyIconView` (DinghyIconView.kt:50-54)
wraps the ligature branch in `clearAndSetSemantics {}` when `contentDescription == null`, suppressing
the leak. The ProbeCalibrate Focus icons in this same diff correctly route through `DinghyIconView`;
these three sites do not.

Note: bare `MaterialSymbol` is used in ~42 places app-wide, so the primitive's leak is pre-existing —
but these specific sites *regressed* from silent-decorative to name-announcing as part of this diff.

**Fix:** Route the decorative status shapes through `DinghyIconView` with `contentDescription = null`
(which applies `clearAndSetSemantics {}`), or wrap the `MaterialSymbol` in `Modifier.clearAndSetSemantics {}`
at each site. For example, in `MoveScreen.StatusShape`:
```kotlin
@Composable
private fun StatusShape(glyphName: String, tint: Color, sizeSp: Float, modifier: Modifier = Modifier) {
    MaterialSymbol(
        name = glyphName,
        modifier = modifier.clearAndSetSemantics {}, // decorative: don't speak the ligature name
        tint = tint,
        sizeSp = sizeSp,
    )
}
```
Apply the same `clearAndSetSemantics {}` to the two `ThemeEditorScreen` overlays.

### WR-02: PrintStatusPreviews KDoc mislabels the theme matrix as the state matrix

**File:** `app/src/main/java/works/mees/dinghy/preview/PrintStatusPreviews.kt:25-26`

**Issue:** The diff find-replaced `[PrintStatusThemeMatrix]` → `[PrintStatusStateMatrix]` on line 26.
The original `[PrintStatusThemeMatrix]` was already a broken link (no such symbol — the theme matrix is
implemented as six separate `PrintStatusThemeColorfulDark/…HighContrastLight` functions at lines
80-105). The "fix" pointed it at `PrintStatusStateMatrix`, but line 26 describes "the FULL 6-theme
matrix on ONE representative state (Printing)" — that is the THEME matrix, not the state matrix. The two
bullets (lines 25 and 26) now both read `[PrintStatusStateMatrix]` while describing two different
things, so the doc is actively misleading.

**Fix:** Point line 26 at the actual theme-matrix symbols (or describe them as a set) instead of
reusing `PrintStatusStateMatrix`:
```
 *  - The six `PrintStatusTheme*` previews — the FULL 6-theme matrix on ONE representative state
 *    (Printing), each a sibling [PreviewBox] seed wrapper.
```

### WR-03: DinghyIcons KDoc still claims FineTune glyphs are "project-local vector drawables (D-17)"

**File:** `app/src/main/java/works/mees/dinghy/designsystem/icons/DinghyIcons.kt:86`

**Issue:** The comment block at lines 82-86 says "The remaining FineTune glyphs below stay project-local
vector drawables (D-17) pending owner review." But the glyphs immediately below it
(`MaxVelocity`/`arrow_shape_up_stack_2`, `MaxAccel`/`sprint`, `MinCruise`/`directions_boat`,
`SquareCornerVelocity`/`rounded_corner`, `PressureAdvance`/`text_select_move_forward_word`,
`SmoothTime`/`avg_time`, `Decrease`/`remove`, `Increase`/`add`, `InputCircle`/`input_circle`) are ALL
`IconRef.Ligature(...)` now — none is a drawable. The KDoc contradicts the code it sits on and will
mislead the next maintainer into thinking local vectors still exist for these (they were deleted this
phase). This is the kind of stale comment that causes a future "why is there no drawable?" goose chase.

**Fix:** Update the comment to reflect that the FineTune glyphs are now Material Symbols ligatures
(consistent with the `MaxVelocity`/`MaxAccel` note two lines above), e.g.:
```
// The FineTune glyphs below now ALSO render the OFFICIAL Material Symbols glyph via the bundled font
// (Ligature) — the 18.1 flip retired their hand-traced local vectors (D-08/D-15).
```

## Info

### IN-01: `DataSwatch` retains the now-unneeded `size` import only via other call sites

**File:** `app/src/main/java/works/mees/dinghy/ui/screen/ThemeEditorScreen.kt:15`

**Issue:** The swap removed the `Modifier.size(fsSp(...).dp)` calls that wrapped the old `Icon` glyphs,
sizing now flowing through `MaterialSymbol(sizeSp = …)`. `import androidx.compose.foundation.layout.size`
is still needed by other `.size(` usages in the file (2 remain), so this is NOT a dangling import — just
flagging that the icon-related `.size()` usages are gone and the import survives only incidentally. No
action required unless those other usages later disappear.

**Fix:** None needed now; revisit if the remaining `.size(` call sites are removed in a later phase.

### IN-02: Console glyph sizing keys off `textSize` (pixels) — correct but fragile to unit drift

**File:** `app/src/main/java/works/mees/dinghy/ui/console/ConsoleRowsAdapter.kt:217`

**Issue:** `val px = (textSize).toInt().coerceAtLeast(1)` relies on `TextView.getTextSize()` returning
**pixels** (it does), to size the compound drawable's square bounds to the fsSp-scaled row text. This is
correct today and the comment documents the intent. Noting it only because a future change that sets
`textSize` in sp via a different setter, or reads a sp value here, would silently shrink/grow the safety
glyph relative to the text — and the glyph is a load-bearing CVD/grayscale safety signal (D-01/D-02).

**Fix:** None needed. If touched later, keep the px-domain invariant explicit (e.g. assert the value
came from `getTextSize()`), since the glyph size is safety-relevant.
